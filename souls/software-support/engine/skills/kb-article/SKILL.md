# TTPOS KB 文章与 canned response（KB Article）
## 输出纪律

回答从结果开始：先给结论、交付物、必要假设或需要用户补充的关键信息，再给细节。可以在内部读取 AGENTS、knowledge、templates 或 MCP 配置，但不要把内部过程写成用户可见开场。不要以“使用 `skill` / 我会按 / 我会先 / 我先读取 / 已确认”开头；除非用户明确要求解释过程或需要说明阻塞原因，否则不叙述工具调用和资产读取过程。


把一条**已解决**的 TTPOS 工单提炼为可复用的标准 KB 文章，并配套 canned response。**用商家的语言**，不塞内部 code。

## 产出物
**标准 KB 文章 + canned response 摘要**（符合 `templates/kb-article.md`）。

## 前置输入
一条已解决工单（含真实根因与验证过的解法）、适用终端/版本/支付方式、相关已有 KB。

## 引用的 knowledge / templates
- 何时沉淀、KCS v6 四要素结构、canned/macros 体系 → `knowledge/support-playbook.md` §6
- 故障域归类（KB 的 category 按域走） → `knowledge/support-playbook.md` §1.3
- KB 骨架 → `templates/kb-article.md`

## 步骤
1. **从已解决工单提炼**（§6.1）：确认根因已定位、解法已验证；KCS 原则——保留交互中的真实上下文。
2. **结构化（KCS 四要素，§6.2）**：Issue（用商家的话）/ Environment（适用终端/版本/支付方式）/ Resolution（编号步骤 + 验证）/ Metadata（按 §1.3 故障域分类 + 标签 + 关联 GitHub issue）。
3. **明确适用范围**：写清适用终端/版本/支付方式，以及**不适用**的边界（防误用，如「全店都不能结账」属故障请直接联系支持）。
4. **生成 canned 摘要**：精简到可直接回复商家，**与 KB 正文口径一致**。
5. **维护标记**：标「最后核对日期 + 适用版本」，过期下架（§6.3）。

## 填好的范例：KB 文章（承接 PromptPay 已扣款未结账工单，脱敏）

**标题：** 客人扫 PromptPay 付了钱，但机器显示「未付款」怎么办

**分类 / 标签（Metadata）：** category=支付 / 泰国本地支付 tags=PromptPay, 已扣款未结账, 回调, kiosk 关联：#REDACTED（GitHub）/ KB-PAY-001

**最后核对日期：** 2026-06-04

### 适用版本 / 范围（Environment）
- 适用：泰国门店扫码支付方式（PromptPay / LINE Pay / TrueMoney 等），客人已实际扣款但单笔仍显示未付款。
- 不适用：**全店所有支付方式都不能结账**（属服务故障，请直接联系支持，勿自行重复收款）；现金/EDC 刷卡未到账（另查 EDC 域）。

### 问题 / 症状（Issue）
客人用银行 App 扫 PromptPay 付了钱、银行也提示扣款成功，但 TTPOS（kiosk/pos）这边还显示「未付款」，订单结不了账。通常只发生在个别支付方式或个别机器上。

### 原因（Cause）
机器要收到支付平台的「付款成功」回执（回调）后，才会把这笔标记为已支付。当回调没及时回来时，机器就会停在「未付款」。这多为支付通道的临时回调问题（个别情况叠加门店网络波动）。

### 解决步骤（Resolution）
1. **先核实是否真的扣款**：让客人看银行 App / 短信确认是否扣款成功。
2. **在收银端（pos）查这笔支付记录**：确认系统侧是否仍为「未支付」。
3. **不要让客人重复付款**：若系统确未记账，本单**改用现金或刷卡(EDC)完成结账**，并记下这笔扫码已付待核账。
4. **把已扣款未结账的订单记录下来**（订单号 + 支付方式 + 金额 + 时间），反馈给支持核账退补。
5. **验证**：换一笔新订单走同一支付方式测试；若仍复现，暂停该机该支付方式并联系支持。

### 仍未解决？
若多台机器或多种支付方式都出现「已扣款未结账」，请立即联系支持（可能是支付通道故障），并提供：门店、终端类型、支付方式、出现时间、是否客人已扣款。

### canned response 摘要（与正文口径一致）
```
你好，关于「客人扫 PromptPay 付了钱但机器显示未付款」，请这样处理：
1. 先让客人确认银行是否真的扣款；
2. 在收银端查这笔记录是否仍未支付；
3. 若确未记账，请勿让客人重复付款，本单改现金或刷卡完成，并记下订单号待核账；
4. 把订单号+金额+时间发给我们核账退补。
详细见：<KB 链接>。若多台/多种支付都这样，可能是支付通道故障，请立即联系我们。
```
> canned 标注：适用 泰国扫码支付（PromptPay/LINE Pay 等）| 最后核对 2026-06-04，过期即下架。

## 交付前自检清单
- [ ] 解决**步骤可复现**（从已知起点、编号、含验证方法），且含「先核实扣款、勿重复收款」的资金保护步骤。
- [ ] **适用版本/范围明确**，且写了不适用边界（全店故障请直接联系支持）。
- [ ] 含与正文**口径一致的 canned 摘要** + 维护标记（最后核对日期 + 适用版本）。
- [ ] 用**商家的语言**（不塞 code 80 / status=0 等内部值，那些只进升级 issue 的代码定位）；未把未确认根因写成确定结论。
- [ ] 不含商户 PII / 工单明文 / 支付密钥 / 网关凭据（已脱敏）。

## 边界（硬骨头与决策点）
- **只沉淀已验证的解法**：根因未定位 / 解法未验证的，先记为「待观察」而非发布 KB。
- **商家语言 vs 工程语言**：KB 给商家看，用通俗话与可执行步骤；内部 code/状态值留给升级 issue 的 `## 代码定位`，不进 KB 正文。
- **口径一致**：canned 与 KB 必须同源，避免 canned 过期误导（§6.3）。
- **知识回流**：升级解决的问题（§3.4）应优先沉淀，闭合「只升级不沉淀」的知识黑洞；TTPOS 经验/等级体系也奖励这种沉淀。
