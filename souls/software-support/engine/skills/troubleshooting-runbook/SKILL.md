# TTPOS 排障 Runbook（Troubleshooting Runbook）

把某**一类 TTPOS 故障**的排查经验固化为「照着走就能定位」的分支 runbook，落到 playbook §1.3 的某个故障域。

## 产出物
**某类故障的排障 runbook**：症状归类 + 采集项（复现五要素 + 该域必收信息）+ 分支排查树 + 已知原因与方案 + 升级判定出口。

## 前置输入
该类问题的典型症状、可拿到的历史 GitHub issue/日志、当前已知原因库。

## 引用的 knowledge / templates
- **TTPOS 故障域速查与必收信息** → `knowledge/support-playbook.md` §1.3
- 复现五要素、分层采集顺序（TTPOS 链路）、已知问题库结构 → `knowledge/support-playbook.md` §4
- 升级触发条件与所需信息、过质量门 → `knowledge/support-playbook.md` §3 / §7 + `templates/escalation-ticket.md`
- 分级 → `templates/sla-matrix.md`

## 步骤
1. **症状归类**：给这类问题一个稳定的「症状指纹」，落到 §1.3 故障域，列出它**像**与**不像**的相邻问题（避免误判）。
2. **采集项**：按 §4.1 + §1.3 该域必收信息列本类必收（针对该类裁剪）。
3. **分支排查树**：按 §4.2 TTPOS 链路分层（商家操作→终端→硬件→网络→server→数据），每个分支给「判据 → 结论 → 下一步」。
4. **已知原因与方案**：按 §4.3 结构列已知原因（症状→触发→绕过→修复状态→关联 GitHub issue）。
5. **升级判定出口**：明确什么条件下停止本层排查、带哪些信息升级（§3.2/§3.3），升级单套质量门（§7）。

## 填好的范例：「ESC/POS 打印机不出单」runbook（脱敏）

> **故障域**（§1.3）：ESC/POS 打印机不出单。**症状指纹**：商家报「单子不出来 / 厨房没收到打印 / 小票机不响」，但收银下单/结账本身正常。
> - **像**：某台打印机不出单、某类单（厨房单/结账单/退菜单）不出。
> - **不像**：结不了账（→走支付/订单故障域）、整机黑屏（→设备硬件）、KDS 屏不亮新单（→KDS/MQTT 故障域）。

**采集项（复现五要素 + 打印域必收，裁剪）**
- 连接方式：**LAN（网口）还是 USB**？打印机型号 / IP（脱敏）。
- 是哪类单：结账小票 / 厨房单 / 退菜单 / 全部？其他单是否正常出？
- 范围：单台还是该店所有打印机？其他终端发起打印是否也不出？
- 环境：终端(pos)、server v2.23.x / flutter v2.22.x、商户(company_uuid 脱敏)、网络。
- 证据：打印机指示灯状态、是否曾换网络/换 USB 口、终端打印日志（脱敏）。

**分支排查树**
```
打印机不出单
├─ 连接方式？
│   ├─ LAN（网口）
│   │   ├─ 打印机 IP 能 ping 通吗 / 同网段吗？
│   │   │   ├─ 否 → 网络/IP 问题 → 让商家确认打印机与 pos 同 WiFi/网段、IP 未变 → 不行升 L2 查 network_printer 连接
│   │   │   └─ 是 → 端口/协议层 → 试重启打印机 + pos 重连 → 仍不出升 L2
│   └─ USB
│       ├─ 换 USB 口 / 重插后识别吗？
│       │   ├─ 否 → 线/口/驱动 → 换线换口；仍不识别升 L2 查 usb_serial 识别
│       │   └─ 是 → 识别但不出 → 下一分支
├─ 是「所有单」还是「某类单」不出？
│   ├─ 某类单（如只厨房单不出） → 打印任务路由/绑定 → 查该类单的打印机绑定配置 → 配置正常仍不出升 L2
│   └─ 所有单 → 打印通道/驱动 → 升 L2
├─ 是「单台」还是「全店打印机」都不出？
│   ├─ 全店 → 网络/服务端打印下发 → 升 L2/L3（可能 server 侧）
│   └─ 单台 → 该机硬件/连接 → 按连接方式分支处理
└─ 其他终端发起打印也不出？
    └─ 是 → 指向打印机本身或网络，而非发起终端
```

**已知原因与方案**
| 症状指纹 | 触发条件 | 临时绕过 | 永久修复状态 | 关联 |
| --- | --- | --- | --- | --- |
| LAN 打印机全不出，ping 不通 | 打印机 IP 被路由器重新分配/换了网络 | 给打印机设固定 IP，pos 重新绑定 | 文档化固定 IP 指引（KB） | KB-PRINT-001 / #REDACTED |
| USB 打印机识别但不出单 | 换过 USB 口/线材老化 | 换原装线 + 固定 USB 口 | — | #REDACTED |
| 仅厨房单不出，结账单正常 | 厨房打印机绑定/分类配置丢失 | 重新绑定厨房打印机到对应出品分类 | 配置校验（待研发评估） | #REDACTED |

**升级判定出口**
- LAN ping 通但仍不出 / USB 识别但不出 / 全店打印机不出 → 本层无 server 权限时升 L2，带：连接方式、型号、是哪类单、范围、已尝试（脱敏）。
- 全店所有终端打印均不出（疑 server 侧打印下发）→ 升 L3，开**过质量门**的 GitHub issue，代码定位起点 `ttpos-flutter/packages/printer`（network_printer.dart / usb_serial / esc_pos_utils_plus）。
- 影响达 P1（单店堂食无法出餐、晚市高峰）→ 提级并视情况联动 `incident-comms`。

## 交付前自检清单
- [ ] **故障域已锁定**（§1.3）；症状指纹有「像/不像」对照（防误判到支付/KDS 域）。
- [ ] **复现五要素 + 该域必收信息齐全**（连接方式 LAN/USB、是哪类单、范围必收）。
- [ ] 分支排查树**每个分支可执行**（有判据 + 结论 + 下一步），非空泛建议。
- [ ] 有明确**升级出口**（条件 + 带什么信息 + 代码定位起点），不会死循环在本层。
- [ ] 已知原因表含「修复状态」，未把「待研发评估」写成确定时间。
- [ ] 日志/IP/型号/商户已**脱敏**。

## 边界（硬骨头与决策点）
- **打印 ≠ 交易故障**：打印不出单本身默认 P2，但若导致堂食无法出餐且高峰无绕过可达 P1；勿与「结不了账」混淆（那是支付/订单域）。
- **先连接后软件**：打印类先排连接（LAN/USB）再怀疑软件/配置，避免直接甩研发。
- **升级出口优先**：runbook 的价值在「何时停、带什么走、定位到哪个文件」，不是穷举所有可能。
- **不臆测根因**：本层只到「指向某层/某文件」，根因结论留给有 server 权限的层级。
