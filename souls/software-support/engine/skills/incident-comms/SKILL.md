# TTPOS 事故沟通包（Incident Comms）
## 输出纪律

回答从结果开始：先给结论、交付物、必要假设或需要用户补充的关键信息，再给细节。可以在内部读取 AGENTS、knowledge、templates 或 MCP 配置，但不要把内部过程写成用户可见开场。不要以“使用 `skill` / 我会按 / 我会先 / 我先读取 / 已确认”开头；除非用户明确要求解释过程或需要说明阻塞原因，否则不叙述工具调用和资产读取过程。

为一次大面积故障产出**一套对内（Lark）+ 对商家**沟通成品，节奏克制、口径一致、只通报已确认事实，涉资金安抚「款项安全、正在核账」。

## 产出物
**事故沟通包**：对商家公告（首条/进展/恢复）+ 对内 Lark 同步 + 时间线 + 复盘要点。

## 前置输入
故障现象与已确认影响范围（哪些门店/市场/支付方式/终端）、当前级别（P0/P1）、责任人、是否涉资金/数据。

## 引用的 knowledge / templates
- 沟通原则、不承诺原则、事故节奏、三幕结构、对内同步 → `knowledge/support-playbook.md` §5
- 沟通骨架 → `templates/incident-comms.md`
- 分级 → `templates/sla-matrix.md`；节奏数字依据 → `knowledge/benchmarks.md` §5

## 步骤
1. **定级与影响评估**：对照 `templates/sla-matrix.md` 确认 P0/P1，列**已确认**影响范围（哪些门店/市场/支付方式，不含猜测）。涉资金（已扣款未记账）单列。
2. **对商家首条**：按 §5.3 首条四要点——承认问题 + 已知影响 + 承诺更新 +（涉支付）安抚「客人款项安全，正在核账」；用通俗语言（商家不是工程师）。
3. **对内 Lark 同步**：按 §5.4，比对外更密更技术（假设/已排除/责任人/下一步/ETA 标估计/对外口径）。
4. **进展节奏**：固定节奏更新（参考每 30 分钟，benchmarks §5），每条**明确下次更新时间**。
5. **恢复 + 复盘要点**：恢复公告 + 时间线 + 无指责复盘（影响/根因/检测/恢复/行动项），涉资金给「核账与退补口径」。

## 填好的范例：泰国多店 PromptPay/LINE Pay 支付回调大面积失败（脱敏）

> **场景**：2026-06-04 19:30 起（曼谷晚市高峰），泰国多家门店反映 PromptPay(80)、LINE Pay(150) 扫码支付后机器持续显示未付款、无法结账，客人多数已实际扣款。20:05 定位为支付回调网关链路异常，20:30 切换备用回调通道缓解，20:55 确认恢复并启动批量核账。

**对商家首条（19:42，Lark 商家群 / 公告）**
> **【处理中】部分门店扫码支付（PromptPay / LINE Pay）暂时无法完成结账**
> 我们已收到泰国部分门店反映：客人扫码支付后机器仍显示未付款、无法结账。技术团队正在紧急处理。
> **客人已支付的款项是安全的，我们会逐笔核账**，请暂时引导客人改用现金或刷卡(EDC)完成结账，并记录订单备查。
> 下次更新：20:15 前。

**对商家进展（20:10）**
> **【已定位】扫码支付结账异常**
> 已定位到与支付回调通道有关，正在切换备用通道恢复。预计影响范围：泰国部分门店的 PromptPay / LINE Pay 扫码支付；现金、EDC 刷卡不受影响。
> 已扣款未结账的订单我们会统一核账，请继续保留订单记录。下次更新：20:40。

**对商家恢复（20:58）**
> **【已恢复】扫码支付结账已恢复**
> PromptPay / LINE Pay 扫码支付已于 20:55 恢复，受影响时段约 19:30–20:55。
> 期间「客人已扣款但未结账」的订单，我们正在批量核账，会逐店反馈处理结果（退款或补单）。给您带来的不便深表歉意，复盘报告 24 小时内提供。

**对内 Lark 同步（19:50，incident 频道）**
```
【事故】泰国多店 PromptPay/LINE Pay 回调失败 级别：P0 责任人：<oncall-A> 状态：定位中
影响：泰国 ≥N 店，支付方式 PromptPay(80)/LINE Pay(150)，晚市高峰；多数客人已实际扣款（资金风险）
当前假设：支付回调网关链路异常，回调未将支付订单 0→1，SaleOrder 未联动结账
已排除：单店配置（多店同现象）、前端缓存（重启无效）、EDC/现金通道（正常）
下一步：切换备用回调通道；准备已扣款未结账订单的批量核账脚本 ETA（估计）：20:30 缓解
对外口径：19:42 Lark 商家群首条已发（引导改现金/EDC），下次 20:15 前
```

**时间线**
| 时间(Asia/Bangkok) | 事件 |
| --- | --- |
| 19:30 | 多店报告 + 监控告警，扫码支付未回调 |
| 19:42 | 对商家首条发布（引导现金/EDC 绕过） |
| 20:05 | 定位：支付回调网关链路异常 |
| 20:30 | 切换备用回调通道，开始缓解 |
| 20:55 | 确认恢复，启动批量核账 |

**复盘要点（无指责）**
- 影响：泰国 ≥N 店、约 85 分钟扫码支付无法结账，多笔已扣款未记账（核账中），现金/EDC 不受影响，无数据丢失。
- 根因：支付回调网关链路异常，回调未把支付订单从未支付(0)更新为已支付(1)，SaleOrder 未联动结账。
- 检测：监控 + 商家报告几乎同时（MTTA 约 12 分钟，可加支付回调成功率告警进一步缩短）。
- 恢复：切换备用回调通道缓解（MTTR 约 85 分钟），缓解路径需预案化。
- 资金处置：已扣款未结账订单按「核账→退款或补单」逐店反馈，对账口径见 §对账。
- 行动项：① 支付回调成功率/超时告警（负责人 <oncall-A>，截止 2026-06-11）；② 备用回调通道一键切换预案（负责人 <release-owner-B>，截止 2026-06-18）；③ 已扣款未结账自动比对脚本常备（负责人 <data-C>，截止 2026-06-18）。

## 交付前自检清单
- [ ] **未承诺未确认的恢复时间**（首条/进展只说「下次更新时间」）。
- [ ] 涉支付的**资金安抚到位**（「客人款项安全、逐笔核账」），并给商家**可立即执行的绕过**（现金/EDC）。
- [ ] 对商家措辞**克制、通俗**（非工程黑话、不暴露内部 code），只含已确认事实。
- [ ] 每条对外更新都**标注了下次更新时间**；多渠道（Lark 群/公告）口径一致。
- [ ] 含**时间线（门店当地时区）+ 无指责复盘**（区分防复发 vs 缩短恢复 + 资金处置口径）。
- [ ] 范例已**脱敏**（无门店 PII、商户号、支付密钥、网关凭据）。

## 边界（硬骨头与决策点）
- **不承诺恢复时间**：即使内部有 ETA，对商家只给「下次更新时间」，ETA 仅对内且标「估计」（§5.2）。
- **资金口径谨慎**：只说「款项安全、会逐笔核账」，不说「一定全额退/一定能补单」，待对账结果。
- **先承认后细节**：首条以承认 + 绕过 + 资金安抚为先，技术细节随定位逐步释放。
- **对外发布需人审**：本 skill 产出文案，正式对商家发布必须经人确认（Phase 2 即使接 Lark/Statuspage MCP 也走草稿+人审，见 integrations.md）。
