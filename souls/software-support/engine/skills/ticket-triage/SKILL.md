# TTPOS 工单分诊与升级（Ticket Triage）
## 输出纪律

回答从结果开始：先给结论、交付物、必要假设或需要用户补充的关键信息，再给细节。可以在内部读取 AGENTS、knowledge、templates 或 MCP 配置，但不要把内部过程写成用户可见开场。不要以“使用 `skill` / 我会按 / 我会先 / 我先读取 / 已确认”开头；除非用户明确要求解释过程或需要说明阻塞原因，否则不叙述工具调用和资产读取过程。

把一条进来的商家问题，稳定推进到「自助解决」或「干净升级」，升级单**直接套 ttpos-bot 5 维质量门**，并产出**具名成品**。

## 产出物
1. **分诊结论**：主类 + 分级（P0–P3）+ 分级依据 + 故障域 + 路由。
2. **升级 GitHub issue**（如需升级）：符合 `templates/escalation-ticket.md`、**能过质量门**的可交付文本。

## 前置输入
商家原始描述、门店/终端信息、是否多店同时报同一现象、是否触及账号/资金/退款、是否营业高峰。

## 输入不足时的硬规则

如果缺少商家原始描述、门店/终端信息、影响范围、涉资金状态等前置输入，**不得编造商家场景、具体商家、时间、金额、服务费、设备状态、复现次数或填好的 issue**。此时不要直接输出完整升级 issue，而是输出：

1. **缺失信息清单**：逐项列出还缺哪些关键事实，并标明为什么会影响分类/分级/升级。
2. **建议先问的问题**：用一线客服可直接复制的短问题采集复现五要素、影响范围、终端/版本、涉资金状态和证据。
3. **可先给商家的保守回执**：只确认已收到、正在核实、会优先处理涉资金/营业受阻风险；不承诺修复时间、退款结果或尚未验证的原因。

只有当输入足以支撑分类、分级、故障域、复现五要素和质量门时，才整理成完整升级 issue。已给足信息的场景可参考下方填好的范例。

## 引用的 knowledge / templates
- 分诊决策树与五类分类、**TTPOS 故障域速查** → `knowledge/support-playbook.md` §1（含 §1.3）
- 分级判定与 SLA → `knowledge/support-playbook.md` §2 + **唯一权威表** `templates/sla-matrix.md`
- 升级矩阵与干净升级所需信息 → `knowledge/support-playbook.md` §3
- **5 维质量门** → `knowledge/support-playbook.md` §7
- 升级 issue 骨架 + 5 维映射 → `templates/escalation-ticket.md`

## 步骤
1. **共情 + 复述确认**（§5.1）：一句共情（尤其营业受阻/涉钱）+ 复述你理解的问题。
2. **分类**：走 §1.2 决策树归唯一主类。多店同现象 / 核心交易链路不可用 → 「故障」，立即提级并启动 `incident-comms`。
3. **锁定故障域**（§1.3）：把现象落到打印/支付/EDC/同步/KDS/开台对账/外卖/多门店之一，按该域「必收信息」采集。
4. **定级（P0–P3）**：按影响面 × 紧急度对照 `templates/sla-matrix.md`；涉资金（已扣款未记账）至少 P1；不确定就高不就低，写明分级依据。
5. **采集复现五要素**（§4.1）：步骤 / 预期 vs 实际 / 环境(终端+版本+商户) / 频率与时间 / 证据（脱敏）。缺项不进升级。
6. **自助解决 or 干净升级**：
   - 能自助：给编号步骤 + 验证方法 + 预防建议（如打印机重连三步）。
   - 需升级：按 `templates/escalation-ticket.md` 整理成**能过 §7 质量门**的 GitHub issue，告知商家下一步与反馈节奏，**不承诺修复时间**；涉资金只说「会核实并回复」。

## 填好的范例：曼谷某店 kiosk PromptPay 已扣款但订单未结账（脱敏）

> **场景**：2026-06-04 19:42（曼谷晚市高峰），某泰国餐厅一台自助点餐机（kiosk）客人扫 PromptPay 付款，银行已扣款，但机器仍显示「未付款」、订单结不了账。同店另一台 kiosk 与 pos 收银正常，仅这台、仅 PromptPay。客人在排队，店长很急。

**分诊结论**
- 主类：**缺陷（Bug）**，含**资金风险**（客人已实际扣款但系统未记账）。
- 故障域（§1.3）：**泰国本地支付回调失败**（PromptPay, code 80）。
- 分级：**P1**。依据（影响面 × 紧急度，对照 `templates/sla-matrix.md`）：影响面 = 单店单终端单支付方式（非全平台），但**涉资金**（已扣款未记账）+ 营业高峰 + 该终端 PromptPay 无法完成结账。涉资金故按「就高」取 P1，不降 P2。
- 路由：L1 先给绕过（核实扣款后改其他支付/现金完成本单，PromptPay 待修），同步升 L3（GitHub issue）核账并定位回调。
- 临时绕过：先在 pos 端核实该笔是否实际入账；若确未记账，本单改现金/其他支付完成，记录待对账退补。

**升级 GitHub issue**（符合 `templates/escalation-ticket.md`，过 §7 质量门）

标题：曼谷某店 kiosk PromptPay 已扣款但 SaleOrder 仍为未结账(status=0)

分级（P0–P3）：P1 | 分级依据：单店单终端单支付方式，但客人已扣款未记账(资金风险)+晚市高峰 → 就高取 P1
来源（Lark/工单）：#REDACTED-LARK | 升级目标：L3（研发）| 故障域：泰国本地支付回调失败(PromptPay)

## 问题描述
kiosk 终端客人扫 PromptPay 付款，银行端已扣款成功，但 TTPOS kiosk 仍显示「未付款」，
对应 SaleOrder 停在未结账状态，无法完成结账。同店另一台 kiosk 与 pos 收银下单/结账正常，
仅此台、仅 PromptPay 方式复现。

## 复现路径
1. kiosk（已绑定该门店）选菜：冬阴功汤 ×1、泰式炒河粉 ×1
2. 进入结账，选支付方式 PromptPay（code 80），生成收款 QR
3. 客人用银行 App 扫码并支付，银行端提示扣款成功
4. 预期：kiosk 收到支付回调 → 支付订单 status=已支付(1) → SaleOrder 转已结账
   实际：kiosk 持续显示未付款，支付订单 status 仍为未支付(0)，SaleOrder 未结账

## 影响范围
- 影响门店/终端：单店 1 台 kiosk（其余终端正常）
- 是否涉资金：是——客人银行已扣款，系统未记账（需核账，可能需退/补单）
- 绕过方案：有——核实扣款后改现金/其他支付完成本单，PromptPay 暂停该机使用
- 频率与首次时间：必现（连续 3 笔同样表现）；首次 2026-06-04 19:42（Asia/Bangkok），晚市高峰

- 版本：server v2.23.x / flutter v2.22.x
- 商户：company_uuid=<REDACTED>，曼谷门店，市场=泰国
- 设备/网络：kiosk 有线网在线，非离线场景

## 交付前自检清单
- [ ] 分级**有明确依据**（影响面 × 紧急度，涉资金就高），对照 `templates/sla-matrix.md`，未自造分钟数。
- [ ] **故障域已锁定**（§1.3），并采了该域必收信息。
- [ ] 升级 issue **过 5 维质量门**：标题无方括号前缀、含 问题描述/复现路径/影响范围/环境 四节、可验证条目 ≥3、环境含终端+版本+商户、有代码定位（自检见 escalation-ticket.md 末尾）。
- [ ] 支付/商户/网关标识已**脱敏**（无密钥、token、PII、连接串）。
- [ ] 给商家回执含下一步与节奏，涉资金只说「会核实并回复」，**未承诺修复时间**。
- [ ] 若涉账号/退款/对账改账/shop 库，**已先验证身份与门店授权**再继续。

## 边界（硬骨头与决策点）
- **升级判定**：信息不全不进升级；宁可多采集一轮，也不让研发从零复现（§3.3）。升级单必须过质量门（§7）。
- **资金优先**：客人已扣款未记账，即使影响面小也快速升级核账，至少 P1（§2.1 / §3.2）。
- **不承诺**：修复时间、上线版本、需求是否采纳一律不对外承诺（§5.2）。
- **身份验证**：商户账号/退款/对账改账/shop 库/设备解绑等敏感操作，**先验证身份与门店授权**再执行。
- 超支持范围（定制开发、商务、价格、法律）明确转交并记录。
