# TTPOS 软件客服 Playbook（方法论 / 框架 / 决策树 / 反模式）

> 引擎参考知识，非百科罗列。所有 skill 通过本文件的 **§1–§7 锚点**引用方法论。
> 基准数字见 `knowledge/benchmarks.md`；SLA/升级矩阵的**唯一权威定义**见 `templates/sla-matrix.md`。
> TTPOS 内部口径（支付方式 code、订单/桌台状态值）以 ttpos-server-go 常量为准（见 §1.3）。
> 数字纪律：凡区间/待核实的口径，本文不写死成「行业唯一标准」；TTPOS 无官方 SLA 合同前，分钟数标「待核实/按合同校准」。

---

## §1 分诊与分类（Triage & Classification）

### 1.1 五类分类与路由

每条进来的商家工单先归到**唯一主类**（决定走哪条流程）：

| 类别 | TTPOS 典型信号 | 路由 | 是否对外承诺 |
| --- | --- | --- | --- |
| 使用咨询（How-to） | 「怎么设置服务费/税费」「自助餐怎么开台」「Grab 菜品怎么映射」 | 给步骤 / 指 KB；可沉淀 canned | 可给确定步骤 |
| 缺陷（Bug） | 行为与预期不符、可复现（如某支付方式结账报错） | 走 §4 排障 → 不解决则 §3 升级（套 §7 质量门） | 不承诺修复时间 |
| 故障（Outage / Incident） | 多店/全平台核心交易链路不可用（支付大面积回调失败、订单同步全线异常） | 立即提级（§2）→ §5 事故沟通 | 只通报已确认事实 |
| 账号 / 资金（Account & Money） | 商户登录、门店权限、退款、对账改账、shop 库数据、设备解绑 | **先验证身份与门店授权**（见边界） | 敏感操作前置校验 |
| 需求 / 建议（Feature Request） | 「希望支持 X 支付」「能不能加桌台地图」 | 记录并转 PM（GitHub feature issue） | **不承诺是否采纳** |

> 反模式：把「支付回调失败」当「使用咨询」让商家「重试一下」却没人排障（商家在丢营业额）；把「多店同时不能结账」误判为单店缺陷而错过提级窗口。

### 1.2 分诊决策树（接单后 60 秒内走完）

```
收到商家工单
 ├─ 是否核心交易链路（开台-点餐-送厨-结账-支付）多店/全平台不可用？
 │    └─ 是 → 归「故障」，立即按 §2 评估 P0/P1，触发 §5 事故沟通流程
 ├─ 是否触及商户账号/门店权限/退款/对账改账/shop 库数据/设备解绑？
 │    └─ 是 → 归「账号/资金」，先做身份与门店授权验证，再继续
 ├─ 行为是否与产品预期不符且可复现（如某支付方式/某终端报错）？
 │    └─ 是 → 归「缺陷」，进入 §4 信息采集与排障，按 §1.3 锁定故障域
 ├─ 是「怎么用 / 在哪设置」？
 │    └─ 是 → 归「使用咨询」，给步骤或 KB 链接
 └─ 是「希望支持某能力」？
      └─ 是 → 归「需求」，记录转 PM（GitHub feature issue），不承诺采纳
```

> 不确定主类时：**就高不就低**先按更严重的分支处理（故障>缺陷>咨询），待信息齐全再降级。营业高峰时段的交易链路问题默认提一级紧急度。

### 1.3 TTPOS 故障域速查（分诊锚点 + 该收什么信息）

接缺陷/故障单时，先把现象落到下面某个**故障域**，再按该域的「必收信息」采集（缩短排障与升级周期）。

| 故障域 | 商家话术信号 | 必收信息（除复现五要素外） | 升级时的代码定位起点 |
| --- | --- | --- | --- |
| **ESC/POS 打印机不出单** | 「单子不出来」「厨房没收到打印」「小票机不响」 | 连接方式（LAN/USB）、打印机型号/IP、是哪类单（结账/厨房/退菜）、其他单是否正常、是否换过网络 | `ttpos-flutter/packages/printer`（network_printer.dart / usb_serial / esc_pos_utils_plus） |
| **泰国本地支付回调失败** | 「客人扫了 PromptPay 付了钱，机器还显示未付」 | 支付方式（PromptPay 80 / LINE Pay 150 / TrueMoney 140 / SCB 100 / KBANK 93xxx）、客人是否实际扣款、SaleOrder/支付订单状态、时间戳 | `ttpos-server-go/main/app/constant/payment.go`（PaymentOrderStatus、PaymentMethodCode） |
| **EDC 刷卡失败** | 「刷卡机刷了没反应/没回执」 | EDC 型号（KBANK LINKPOS）、USB 是否识别、银行回执码 | `ttpos-flutter/packages/edc`（HYPERCOM / USB CDC ACM） |
| **离线同步差异** | 「断网时下的单，恢复网络后对不上 / 重复」 | 断网时段、涉及单号、本地是否成功、恢复后表现 | 同步任务（sync_task）+ 订单状态比对 |
| **KDS 不接单 / QDS 不叫号** | 「后厨屏不亮新单」「叫号屏没更新」 | 是哪个 KDS/QDS、是否全部不接还是部分、MQTT 是否连上、网络 | `ttpos-flutter/packages/mqtt`（mqtt5_client）+ OrderProduct 接单状态 |
| **开台/转台/对账差异** | 「转台后菜没跟过去」「日结对不上」「抹零金额不对」 | 桌台号、操作序列（开台 OPEN_TABLE/转台 CHANGE_TABLE）、Desk 状态、SaleBill 金额构成（服务费/税费/抹零规则） | `ttpos-server-go/main/app/constant/{desk.go,order.go}` |
| **Grab / LINE MAN 外卖对接** | 「Grab 单没进系统 / 菜品对不上」 | 平台（Grab 91100 / LINE MAN 91200）、外送单号、菜品映射、状态回传 | 外卖单 source/支付 code 映射 |
| **多门店数据隔离** | 「看到别的店的数据」「连锁报表对不上」 | 商户 company_uuid、门店、登录账号角色、是哪张表/报表 | saas 库（ttpos_company）vs shop{company_uuid} 库定位 |

> 反模式：不锁故障域就泛泛排障；把「客人已扣款但显示未付」当普通缺陷而不立即标资金风险（应进 §2 资金维度，至少 P1）。

## §2 分级与 SLA（Severity & SLA）

### 2.1 P0–P3 判定 = 影响面 × 紧急度

判定用「影响面（Impact）× 紧急度（Urgency）」优先级矩阵，**不靠单一维度**：

- **影响面**：单店 / 连锁 / 全平台 × 是否核心交易链路（开台-点餐-送厨-结账-支付）× 是否涉资金（已扣款/对账/退款）。
- **紧急度**：是否营业高峰时段、是否有可用绕过方案（如改现金收款）、是否在持续恶化。

| 级别 | 语义判定 | TTPOS 例 |
| --- | --- | --- |
| **P0** | 核心交易链路阻断 / 大面积不可用 / 资金风险，无绕过 | 多店支付全部回调失败、全平台无法结账、订单同步全线丢单、商家数据跨租户泄露 |
| **P1** | 严重影响主流程，无可用绕过，但影响面有限 | 单店所有 ESC/POS 打印机不出单（堂食无法出餐）、某支付方式全店不可用且无现金绕过 |
| **P2** | 一般问题，**有绕过方案**或影响非核心 | 某终端报表导出偶发失败（可换设备）、单台 KDS 不接单（其他屏正常） |
| **P3** | 轻微 / 体验类 / 单点低影响 | 菜单文案错别字、非阻断 UI 瑕疵、单笔历史对账细项疑问 |

> 各级**响应/解决 SLA 的权威口径见 `templates/sla-matrix.md`**（本 soul 采用单一矩阵，禁止在不同文件写不同分钟数）。**TTPOS 暂无官方 SLA 合同，分钟数为通行区间口径，待核实、按合同校准**（依据见 benchmarks.md）。
>
> 反模式：把 SLA「响应时间」与「解决时间」混为一谈。Response SLA 在工单分配到组时触发、在开始处理时停止；Resolution SLA 在创建时触发、在 Resolved 时停止（口径来源见 benchmarks.md）。

### 2.2 时钟排班
- P0/P1 通常 **24×7**（时钟不停，持续处理至恢复）——餐厅营业时段长，晚市/周末正是高峰。
- P2/P3 通常 **8×5 工作日**（夜间/周末时钟暂停）。
- **特例**：泰国/中国/日本跨时区，按**门店当地营业时段**评估紧急度，不按客服所在地。

## §3 升级矩阵（L1 / L2 / L3 Escalation）

### 3.1 职责边界

| 层级 | TTPOS 职责 | 承接量（参考） |
| --- | --- | --- |
| **L1（一线客服）** | 初次接触、基础问题（设置查询、常见 how-to、设备重连指引）、按 SOP/KB、分诊定级、采集复现五要素 | 约 70–80% 来单（区间，源见 benchmarks.md） |
| **L2（技术支持）** | 复杂技术问题、深入排障、日志分析、支付/打印/同步/外卖集成故障，必要时联动研发 | L1 升级单 |
| **L3（研发，GitHub）** | 系统级故障、server/shop 库级问题、代码修复、根因定位 | L2 升级单（= 过质量门的 GitHub issue） |

> 原则：**尽量在最低层级解决**；问题超出本层技能 / 需更高权限或代码改动时升级。升级到 L3 = 在 GitHub 开一条**能过 §7 质量门**的 issue。

### 3.2 升级触发条件（任一满足即升级）
- 已走完本层 SOP/runbook 仍未解决，且影响达 P0/P1。
- 需要本层无权限的操作（server/shop 库访问、改配置/代码、查后端日志、对账改账）。
- 怀疑根因在产品/server/支付网关/外卖平台而非门店环境（网络/设备）。
- 涉资金风险（客人已扣款但系统未记账）——即使影响面小也要快速升级核账。
- SLA 解决时钟将到期且无进展。

### 3.3 干净升级所需信息（升级单缺一不进 L2/L3，且要过质量门）

升级单完整性**直接决定** L2/L3 解决速度，且 TTPOS 下**升级单 = GitHub issue，必须过 §7 5 维质量门**。必备：
- **复现五要素（§4.1）**（含 §1.3 该故障域的「必收信息」）。
- **分级依据**（影响面 × 紧急度）。
- **已尝试方案**（每步 → 结果）。
- **影响范围**（单店/连锁/全平台、是否涉资金）。
- **脱敏日志/证据** + **代码定位**（指向 §1.3 的起点文件/常量/终端）。

骨架与 5 维映射见 `templates/escalation-ticket.md`。

### 3.4 反馈回路（向下流动）

L3 解决后（GitHub issue close 时），**解法是什么 / 为何有效**必须回流到 L1/L2，并沉淀为 KB（§6），否则同类问题会重复升级。ttpos-bot 的经验/等级体系正是奖励这种「问题→可复用沉淀」的闭环。

> 反模式：把工单「甩」给 L2 却不附上下文（让研发从零复现）；L3 修完不回灌知识（知识黑洞）；GitHub issue 标题写「支付有问题」（过不了质量门，见 §7）。

## §4 排障方法论（Troubleshooting）

### 4.1 复现五要素（信息采集，缺项不进升级）

1. **复现步骤**：从**已知起点**开始、编号、含确切输入值与时序（如「开台→点 2 份冬阴功→送厨→结账选 PromptPay」）。
2. **预期 vs 实际**：明确应发生什么 / 实际发生什么（既证存在也用于验证修复）。
3. **环境**：**终端**（pos/kds/kiosk/tablet/member…）+ **版本**（server v2.23.x / flutter v2.22.x）+ **商户**（company_uuid / 门店，脱敏）+ 设备/网络（LAN/USB/弱网）。→ 这正是过质量门 `context_links` 维的「终端+版本+商户」。
4. **频率与时间**：必现/偶发、首次发生时间（含时区）、影响门店/终端数、是否高峰时段。
5. **证据**：截图/录屏 + 终端日志/服务端日志/支付回执（**脱敏**：去除支付密钥、商户 token、会员 PII、shop 库连接串）。

### 4.2 分层采集顺序（TTPOS 链路）

`商家操作 → 终端（Flutter app 状态/日志）→ 硬件（打印机 LAN/USB、EDC、MQTT 连接）→ 网络（在线/离线/弱网）→ server 接口（状态码/支付回调/同步任务）→ 数据（saas 库 vs shop{uuid} 库、订单/支付/桌台状态值）`。逐层缩小范围，记录每层「正常/异常」结论。

### 4.3 已知问题库结构（与 §6 KB 联动）

每条已知问题：**症状指纹 → 触发条件 → 临时绕过 → 永久修复状态 → 关联 GitHub issue/KB**。排障先查已知库再开新调查。TTPOS 常见临时绕过：支付回调失败先核实客人是否实际扣款再决定改现金；打印机不出单先重连 LAN/换 USB 口再判软硬件。

> 反模式：未采集复现信息就反复让商家「重启机器」；把「无法复现」当「不是 bug」直接关单（应记录为待观察 + 采集更多证据，支付/同步类尤其要留痕）。

## §5 沟通（Communication & Incident Comms）

### 5.1 日常话术结构

回复 = **共情（一句）→ 复述确认 → 编号步骤 → 下一步与跟进节奏**。
商家在营业受阻时情绪高（直接关系到当天营业额）：先承认影响、给可立即执行的临时绕过（如改现金、换网络），再把对话拉回**事实与下一步**，不与情绪对线，不做无法兑现的承诺。

### 5.2 不承诺原则（硬骨头）
- 不承诺**未确认**的修复时间 / 上线版本。
- 不替研发对外承诺需求**是否采纳**。
- 涉资金（已扣款未记账）只承诺「会核实并回复」，不承诺「一定能退/一定能补单」，待对账结果。
- 只通报**已确认**的事实；未确认的用「正在排查 / 下次更新时间」表述。

### 5.3 事故对外（对商家）沟通节奏（incident）
- **首条最重要**：快速承认问题 + 简述已知影响（哪些门店/功能）+ 承诺后续更新 +（如涉支付/资金）安抚「客人款项安全，正在核账」。用**通俗语言**（商家不是工程师），多渠道（Lark 群/公告）口径一致。
- **节奏**：事故启动后尽快发首条（参考 PagerDuty：5 分钟内首条、再 5 分钟内补影响范围）；之后**固定节奏更新**（参考 Atlassian Statuspage：约每 30 分钟，或视情况），每条**明确下次更新时间**（来源见 benchmarks.md）。
- **生命周期三幕**：首次通报 → 期间更新 → 恢复 + 复盘（post-mortem）。

### 5.4 对内同步（飞书 Lark incident 频道）

对内同步比对外更密、更技术：当前假设、已排除项、责任人、下一步、ETA（标「估计」）、对外口径。骨架见 `templates/incident-comms.md`。

## §6 知识沉淀（KCS Knowledge Capture）

### 6.1 何时沉淀
高频 / 典型 / 升级后定位到根因的问题 → 沉淀为 KB（飞书知识库 / GitHub）。**KCS 原则：在交互过程中实时捕获**（保留真实上下文、立即可复用），不事后补写。

### 6.2 KB 文章结构（KCS v6 四要素）
1. **Issue（问题/症状）**：用**商家自己的话** + 标准化症状指纹（落到 §1.3 故障域）。
2. **Environment（环境/适用范围）**：适用终端 / server/flutter 版本 / 支付方式。
3. **Resolution（解决步骤）**：可复现的编号步骤 + 验证方法（商家自助语言）。
4. **Metadata（分类/标签/关联）**：category（按故障域）、tags、关联 GitHub issue/KB。

骨架见 `templates/kb-article.md`。原则：**用商家的语言**（非研发黑话、非内部 code）；文章**不必完美**，可演进。

### 6.3 canned response / 宏（macros）
高频回复标准化为 canned（如「PromptPay 显示未付怎么办」「打印机不出单先做这三步」），必须**与对应 KB 关联、口径一致**；每条 canned 标注「最后核对日期 + 适用版本」，过期即下架。

> 反模式：KB 写成研发口吻或塞内部 code（商家看不懂）；canned 与产品现状脱节（误导商家）；只升级不沉淀（知识黑洞，§3.4）。

## §7 升级工单的 TTPOS 质量门（ttpos-bot 5 维评分，硬约束）

> **升级到 L3 = 在 GitHub 开 issue，由 ttpos-bot 评 5 维质量门。** 客服开的升级单（bug 类）必须按本节写、能过门。骨架与逐条对照见 `templates/escalation-ticket.md`。

### 7.1 5 个维度（每维 0–2 分）

| 维度 | 满分 2 的标准（bug） | 客服怎么做到 |
| --- | --- | --- |
| `title_specificity` | 唯一动作 + 症状，无歧义；**禁用 `[POS]`/`[FEAT]` 之类方括号前缀**（带前缀最高只给 1） | 标题写「曼谷某店 kiosk PromptPay 已扣款但 SaleOrder 仍为未结账(status=0)」，不写「支付有问题」 |
| `narrative_completeness` | 问题 + 复现 + 影响 都齐全且实在 | 正文含 `## 问题描述` / `## 复现路径` / `## 影响范围` 三节，均有实质内容 |
| `verifiable_items` | **≥3 条可验证条目**（bug 的复现/影响要点） | 复现路径分步可执行 + 影响范围列可核对项，凑齐 ≥3 条 testable bullet |
| `code_locality`（**仅咨询，不卡门**） | `## 代码定位` 有具体指针（文件路径/符号/模块） | 引 §1.3 起点，如 `ttpos-server-go/.../constant/payment.go` 的 `PaymentOrderStatusUnPay=0` |
| `context_links` | 关联 issue，或 bug 的 **终端+版本+商户** 三者齐全 | `## 环境` 写全：终端(kiosk) + 版本(server v2.23.x) + 商户(company_uuid，脱敏)；有相似 issue 就链上 |

### 7.2 gating 口径（务必记牢）
- **gating = 4 维**（`title_specificity` + `narrative_completeness` + `verifiable_items` + `context_links`），**满分 8**。
- `code_locality` **不计入卡门**（advisory-only），但仍要写——它喂给评分提示、加速研发定位、也是客服专业度的体现。
- ttpos-bot 还会按**正文小节**做元数据评分：bug 类必备 `问题描述 / 复现路径 / 影响范围 / 环境` 四节（标题用这些词或其别名，否则匹配不到）。

### 7.3 反模式
- 标题带 `[支付]`/`[POS]` 前缀（`title_specificity` 被压到 ≤1）。
- 只有叙述没有可验证条目（`verifiable_items=0`）。
- bug 不写终端/版本/商户（`context_links` 拿不到 2）。
- 正文小节用了奇怪标题（如「描述」而非「问题描述/问题/现象/症状」），元数据匹配不到而扣分。
