# HR Playbook · 方法论 / 框架 / 反模式（TTPOS 中国团队）

引擎参考。锚定 **TTPOS（餐饮 POS SaaS，中国 + 泰国出海）中国团队**招聘：Go 后端 / Flutter / PM / 客服（可含销售）。每节给「框架 + 判据 + 反模式」。数字与来源详见 `benchmarks.md`。技术栈证据来自 `ttpos-server-go`、`ttpos-flutter`、`ttpos-bot` 仓库。

---

## 1. 招聘需求与人才画像

**框架**
- **编制对齐三问**：① 这是新增编制还是替补？② 该岗位解决什么业务问题、不招会怎样？③ 预算、职级、汇报线、决策人、用人时间线？答不上来就不开始写 JD。
- **胜任力模型（competency model）**：把岗位拆成 4 类维度——
  1. **硬技能 / 专业能力**（可考核的知识与技术栈——见 §3 各岗真实维度）
  2. **问题解决 / 业务理解**（分析、判断、结果导向；技术岗叠加**餐饮 POS 领域理解**）
  3. **协作与沟通**（跨职能、向上管理、影响力；TTPOS 走飞书 Lark + GitHub Issues + ttpos-bot）
  4. **价值观 / 文化匹配**（与团队工作方式一致：线上质量 owner 意识、写得清的 issue）
  每个维度按目标职级写出「这一级应表现成什么样」的行为锚点（behavioral anchor）。
- **人才画像（persona）**：
  - **Go 后端**：多在做后端 / 微服务 / 高并发交易类系统（支付 / 订单 / 电商 / SaaS），熟 Gin/GORM 或同类，关注稳定性与数据一致性。
  - **Flutter**：多在做跨端 App / 大型 Flutter 项目，熟状态管理（GetX/Riverpod/Bloc）与 monorepo，关注多端一致与性能。
  - **PM**：多在做 B 端 / SaaS / 行业软件（最好餐饮 / 零售 / 连锁 / 收银 / ERP），能下沉到门店真实流程。
  - **客服**：多在做 SaaS / 软件 / IT 技术支持，能把商家口述故障翻译成可复现事实。

**判据**：胜任力维度必须**可在面试中被证据验证**（对应 §3 评分锚点）；要求与目标职级匹配（不能用 P7 要求招 P5 预算）；技术岗的领域理解（餐饮 POS）作为加分或区分项，不要当硬门槛把人池砍光。

**反模式**：照抄别家 JD；把「老板想要的全部优点」堆成超人画像（要求又懂 Go 又懂 Flutter 又懂泰语又懂餐饮）；编制没批就启动；用「学历 / 年龄 / 性别」等与绩效无关且涉歧视的硬门槛。

## 2. JD 与渠道

**框架**
- **JD 结构**：岗位概述（一句话讲清解决什么问题，落到 TTPOS 真实业务，如「负责收银 / 桌台微服务稳定性」）→ 核心职责（5–8 条、动词开头、可衡量）→ 任职要求（必备 vs 加分**分开列**）→ 胜任力维度（呼应 §1/§3，供面试官对齐）→ 团队亮点 / 差异化（TTPOS 吸引点：真实交易系统、多端 / 出海、技术自主权）。
- **渠道与漏斗**：分职能选渠道——研发（Go/Flutter）偏内推 / 技术社区（掘金 / GitHub / Gopher / Flutter 中文社区）/ Boss 直聘 / 拉勾；PM 偏内推 + 垂直社区 + 行业（餐饮 / SaaS）熟人；客服 / 销售偏 Boss / 58 / 行业熟人。用 `benchmarks.md` 的漏斗思路监控「渠道→面试→offer→入职」转化，淘汰低质渠道。
- **必备 vs 加分纪律**：必备项是硬门槛（缺则淘汰），加分项是排序权重（影响优先级），二者不可混。餐饮 POS 领域经验、泰语、出海经验通常放**加分**而非必备。

**判据**：JD 每条职责能对应一个可衡量产出；必备项数量克制（过多 = 人才池枯竭）；无歧视性 / 套话表述；技术栈写**真实在用的**（Gin/GORM/MySQL/Redis；Flutter/GetX/Dio/Freezed/Melos）而非堆时髦词。

**反模式**：必备项写 15 条；用形容词（「优秀的」「资深的」）代替可验证标准；渠道只挂一个招聘网站坐等；JD 写一堆公司没在用的技术栈充门面。

## 3. 结构化面试（STAR / BEI）+ 四岗真实能力维度

**框架**
- **为什么结构化**：结构化面试预测效度 **r ≈ .51**，远高于非结构化 **.38**（新研究继续下修至约 .19）；与 GMA / 认知测验并列单一最强预测器，组合可达 **.63**（见 `benchmarks.md`）。这是「必须结构化」的硬论据。
- **STAR / BEI 题目设计**：行为事件访谈（BEI）问**过去真实行为**而非假设：「讲一个你……的具体例子」，追问 **S**ituation / **T**ask / **A**ction / **R**esult。每个胜任力维度配 1–2 道行为题。
- **技术岗双轨**：行为题（BEI）+ **能力实证**（系统设计 / code review / 现场排查 / 看真实代码片段）。能力维度要落到 TTPOS 真实技术栈，避免泛问「你熟悉并发吗」。

### 3.1 Go 后端工程师 能力维度（对齐 ttpos-server-go）

| 维度 | 真实评估点（据 TTPOS 技术栈与规范） | 怎么验（题型） |
|---|---|---|
| Go 语言 / 并发 | goroutine / channel / context 取消 / sync 原语；**按业务键加锁防并发**（TTPOS 开台 / 转台用 UUID 锁 `LockUuid(deskUuid)`） | 让其讲一次真实并发 bug 的定位与修复；现场设计「同桌并发开台」的防护 |
| Gin + GORM | 路由 / 中间件 / 参数校验；GORM 预加载（防 N+1）、事务、索引、分页；Repository 只传 `db` 不传 `dbm` | 看一段 GORM 查询能否指出 N+1 / 缺索引 / 事务边界问题 |
| 微服务 / 通信 | 服务边界、gRPC（外送）、WebSocket（实时）、Redis 缓存与 DelayQueue、**事件总线**（发布 / 订阅订单事件） | 让其设计「下单 → 厨显 / 库存 / 会员」的事件驱动拆解 |
| 数据一致性 / 多租户 | saas 库 + 每店 `shop{uuid}` 库的多租户隔离；幂等 / 对账 / 补偿；金额与库存一致性 | 设计「支付回调重复到达」的幂等方案；问对账差异如何定位 |
| 工程素养 | 错误返回不 panic、命名规范（ID 大写 / URL snake_case）、单测（支付 / 订单高覆盖）、可观测（SkyWalking） | code review 一段代码，看其能否提出工程化改进 |

### 3.2 Flutter 工程师 能力维度（对齐 ttpos-flutter）

| 维度 | 真实评估点（据 TTPOS 技术栈与规范） | 怎么验（题型） |
|---|---|---|
| Flutter / Dart | Widget 树 / 生命周期 / 渲染性能、异步（Future/Stream）、空安全；构建优化 | 让其讲一次卡顿 / 重建过多的性能优化经历 |
| 状态管理（GetX） | GetX 的 controller / 响应式 / 路由 / 依赖注入；状态边界与内存管理（如双屏 `LanguageController` / `LanguageSecondController`） | 设计一个「收银台多状态联动」的 controller 拆分 |
| 网络 / 数据层 | Dio 拦截器 / 错误处理 / 重试；Freezed 数据模型与 codegen；API 层与 model 层分离 | 看一段 Dio + Freezed 代码能否指出问题 |
| Monorepo 工程 | Melos 多包工作区、4 层依赖（app→ui→api/components/i18n→model/logger/shared）**禁反向依赖**、build_runner、10 终端复用 | 问如何在 17 包 monorepo 里加一个跨端复用组件而不破坏分层 |
| 高风险模块意识 | 支付 / 订单模块 **100% 测试覆盖**要求；多端 / 多语言（10 语言）/ 离线一致性 | 问其如何为支付流程设计测试与离线容错 |

### 3.3 产品经理 PM 能力维度（对齐 TTPOS 业务 + ttpos-bot 流程）

| 维度 | 真实评估点 | 怎么验（题型） |
|---|---|---|
| 餐饮 POS 业务理解 | 堂食 / 打包 / 外送、开台 / 转台 / 合台 / 买单、桌台 / 区域、KDS/QDS、自助餐、会员、外卖聚合（Grab/LINE MAN） | 让其拆解「自助餐计时计价」或「桌台地图」的需求要点与边界 |
| 多租户 / 出海 sense | saas + `shop{uuid}` 多租户、连锁 Company/Shop、10 终端、泰国市场（PromptPay/LINE Pay）与本地化 | 问一个功能在「单店 vs 连锁 vs 跨市场」下的差异 |
| 需求与优先级 | JTBD、机会评估、RICE/Kano、写**能过 ttpos-bot 质量门**的 issue（title_specificity / narrative_completeness / verifiable_items / context_links 满分 8） | 给一个模糊需求，让其现场写一条能过质量门的 issue |
| 协作与节奏 | 与研发 / 客服在飞书 + GitHub 协作；sprint 评分（urgency + estimateFit(13-SP) + age）与超期阈值（triage>2/低优>7、in_progress>3、review>1） | 问其如何决定一个高优需求进不进当前 sprint |

### 3.4 软件客服 能力维度（服务 TTPOS 餐厅商家）

| 维度 | 真实评估点 | 怎么验（题型） |
|---|---|---|
| 共情与情绪稳定 | 面对营业高峰出故障、情绪激动的店长 / 收银，先稳情绪再排查 | 角色扮演：高峰期打印机不出单、商家催 |
| POS 故障分诊 | ESC/POS 打印机不出单（LAN/USB）、支付回调（微信 / 支付宝 / 泰国本地 / EDC 刷卡）、离线同步、KDS 不接单、开台 / 转台 / 对账差异、外卖对接、多门店数据隔离 | 给一个故障描述，让其问出复现五要素并初判分级 |
| 工程化复述 / 升级 | 把口述翻译成可复现事实，写出能过 **ttpos-bot 5 维质量门**的 GitHub issue（标题具体、叙述完整、可验证项、代码定位、上下文链接） | 让其把一段商家口述改写成一条合格 issue |
| 工具与流程 | 飞书 Lark + GitHub Issues + ttpos-bot；知识沉淀（KB / canned response） | 问其如何把高频问题沉淀成标准答复 |

- **评分锚点（1–5 rubric）**：每维度写出 1/3/5 分各对应什么行为证据（behaviorally anchored rating scale）。例：Go 并发维度 1=只会用锁不知为何加；3=能为开台场景正确按业务键加锁；5=能权衡锁粒度 / 无锁方案并讲清一致性取舍。
- **面试官分工与校准**：不同面试官分管不同维度（避免重复 + 漏覆盖）；用同一评分卡；面试后做**校准会（calibration）**对齐打分尺度。技术岗建议至少一轮由资深研发做能力实证。

**判据**：每维度有锚点；题目能**区分高低绩效**（问完能据答案给出 1–5 而非「感觉不错」）；技术维度落到 TTPOS 真实栈；先打分再讨论（防锚定 / 从众）。

**反模式**：闲聊式面试；问假设题（「如果……你会怎么做」易被表演）；技术岗只问八股不看真实代码 / 设计；脑筋急转弯；只凭「眼缘 / 像不像我们的人」；面试官各打各的从不校准。

## 4. 薪酬与 offer

**框架**
- **薪档与分位**：调研以百分位报告 **P25 / P50（市场中位）/ P75**。定位策略：P25 = 保守 / 初级或成本敏感岗，P50 = 平衡竞争力，P75 = 抢顶尖 / 难招人才。TTPOS 中国团队里 Go 后端 / Flutter 常较稀缺（偏 P50–P75），客服偏 P25–P50（按城市与经验）。
- **compa-ratio** = 个人薪资 / 薪档中点 ×100%；**range penetration** = (薪资−min)/(max−min)，看个人在薪档内位置。薪档宽幅常设中点的 **80%–120%** 或 **70%–130%**。
- **offer 要素**：职级、薪资结构（base + 浮动 / 奖金 + 期权 / 股票若有）、入职日期、试用期与目标、签字栏。
- **谈判与让步空间**：先定**带宽分位区间**与底线，再分阶段让步（先给区间不给点位、用总包而非单 base 谈、非现金项（期权 / Title / 发展 / 远程弹性）做补充筹码）。**具体薪资数字须来自公司实际购买的调研（本 soul 不内置数值）。**

**判据**：薪酬数据脱敏；分位口径全程一致（别 P50/P75 混用）；offer 与目标职级、内部公平（同级 compa-ratio 不畸高）对齐；草稿标「需法务 / 负责人审批」；无授权不承诺。

**反模式**：拍脑袋报价 / 被候选人牵着加价；只比 base 忽略总包；offer 超内部同级造成倒挂；口头承诺写不进 offer 的条件；把保密薪资数据明文外传。

## 5. 职级与绩效（含 OKR）

**框架**
- **职级带**：TTPOS 这类规模公司宜**自建** 3–5 级简化序列（如 工程师 / 高级 / 资深 / 专家 / 架构师），每级写清「范围、自主性、影响力」的行为描述；用大厂 P 序列做**外部对标**（非官方映射，仅参考）而非照搬。研发与 PM 可分别建序列。
- **OKR 制定**（Google re:Work 口径）：每周期 **3–5 个 Objective**，每个 O 约 **3 个 KR**；KR **0.0–1.0** 打分，最优落点 **0.6–0.7**（总是 1.0 说明不够进取）；KR 必须**可量化、描述结果非活动**（出现「协助 / 分析 / 参与」= 活动，要改成其影响）；KR 须有「可获得、可信、易查」的完成证据；目标成功率约 **70%**。对齐做纵向（对上级 / 公司 O）+ 横向（跨团队依赖）。TTPOS 研发 OKR 的证据来源天然有：故障管理、APM（SkyWalking）、工单系统、ttpos-bot sprint / 质量门数据。
- **绩效校准（calibration）**：跨团队拉齐评级尺度，防止「宽松经理 vs 严格经理」造成不公；用统一证据与分布讨论。
- **晋升答辩**：候选人按职级行为描述自证「已稳定在下一级表现」，委员会据证据而非资历投票。

**判据**：KR 可量化、O 有方向性；避免把 to-do 当 KR；职级行为描述能区分相邻两级；校准后评级分布合理且有据。

**反模式**：把任务清单包装成 KR（「完成 X 需求」是活动）；O 写成「做完 X」而非「达成什么影响」；KR 全设成稳拿 1.0；职级靠工龄 / 资历而非能力；不校准导致评级通胀或打架。

## 6. 员工关系与合规

> 法律要点为方法参考，不构成最终裁决；落地文件须经法务 / 外部律师**送审**。

**框架**
- **入职 / 离职 SOP**：入职走 30-60-90（见 `templates/onboarding-checklist.md`），技术岗 30 天要上手开发环境（Go `go mod` / Flutter `melos bootstrap` + `build_runner`）与领域；离职做交接清单 + 账号 / 仓库权限回收（GitHub / 飞书 / 服务器 / 密钥）+ 离职面谈 + 合规结算。
- **劳动法要点（中国《劳动合同法》）**：
  - **试用期**：合同 3 月–1 年 ≤1 月；1–3 年 ≤2 月；3 年以上 / 无固定期限 ≤6 月；同一员工只能约定一次；试用期工资 ≥ 同岗最低档 / 约定的 80% 且不低于当地最低工资。
  - **经济补偿 N**：每满 1 年付 1 个月工资；6 月–1 年按 1 年；不满 6 月付半个月。
  - **代通知金 +1（N+1）**：仅适用第四十条三种情形（医疗期满不能胜任原岗 / 不能胜任经培训调岗仍不能胜任 / 客观情况重大变化）且未提前 30 日书面通知时，额外付 1 个月工资。**并非所有解除都有 +1**；违法解除走 2N（赔偿金）。
  - **竞业限制**：限制期 ≤2 年，须按月付补偿金（地方口径，待核实）；技术岗涉核心代码 / 架构时才有必要，范围与对象要克制。
  - **工时**：标准工时 / 综合 / 不定时（后两者需审批）；加班受上限与加班费约束。
- **PIP（绩效改进计划）**：用于「不能胜任」的合规处置——明确目标、衡量标准、辅导与节点、改进期；过程留痕，结果与下一步（转正常 / 调岗 / 依法解除）挂钩。注意：PIP 是改进工具，不是「走人前置流程」，滥用易构成违法解除。
- **个人信息保护（PIPL）**：最小必要原则——招聘只收必要信息、明示告知目的、不超范围留存、离职后按规定删除 / 匿名化；敏感个人信息（健康、生物识别）门槛更高。**注意 TTPOS 是多市场（含泰国）公司，跨境员工 / 数据涉境外用工与数据出境时另有合规口径，须单独送审，不在本 soul 范围。**

**判据**：解除路径与补偿口径正确（N / N+1 / 2N 不混）；试用期不超期、不二次约定；PIP 有客观标准且留痕；候选人 / 员工个人信息全程脱敏与最小化；离职技术岗的仓库 / 服务器 / 密钥权限按时回收。

**反模式**：把 N+1 当成所有解除的标配；用 PIP 走过场逼人离职；竞业不付补偿就主张限制；招聘表单超范围收集个人信息；离职不回收 GitHub / 服务器 / 密钥权限；保密薪资 / 个人信息明文外发。
