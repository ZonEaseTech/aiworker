# 30-60-90 入职计划 + 试用期目标（TTPOS 岗位）
## 输出纪律

回答从结果开始：先给结论、交付物、必要假设或需要用户补充的关键信息，再给细节。可以在内部读取 AGENTS、knowledge、templates 或 MCP 配置，但不要把内部过程写成用户可见开场。不要以“使用 `skill` / 我会按 / 我会先 / 我先读取 / 已确认”开头；除非用户明确要求解释过程或需要说明阻塞原因，否则不叙述工具调用和资产读取过程。

**产出物**：一份**入职 checklist（首日 / 首周）+ 30-60-90 计划 + 试用期转正评估标准**，可直接交直属上级与新人执行。工程师计划要含上手真实技术栈与领域。

## 前置输入（缺则先问）

岗位族与职级、入职日、试用期时长（≤法定上限）、直属上级与导师 / Buddy、岗位首个里程碑（落到 TTPOS 真实模块 / 终端 / 业务线）、关键干系人名单。

## 引用资产

- 方法论：`knowledge/hr-playbook.md` §6（入职 SOP、试用期合规、PIPL）+ §3（对应岗位能力维度，作为转正硬指标依据）。
- 骨架：`templates/onboarding-checklist.md`。
- 技术上手参考：`AGENTS.md` 公司语境（Go `go mod tidy` / Flutter `melos bootstrap` + `build_runner`；飞书 + GitHub + ttpos-bot 协作流）。

## 步骤

1. **首日 / 首周**：按 checklist 配齐账号设备权限（GitHub / 飞书 / 服务器 / 开发环境）、必读制度、关键干系人 1:1、首个 low-risk 小任务。工程师首周要**跑通本地开发环境**。
2. **30-60-90 拆解**：每阶段写**可衡量**目标（30 理解上手 → 60 独立产出 → 90 形成影响 / 达转正标准）+ 评估方式；目标落到 TTPOS 真实模块。
3. **关键干系人**：列 1:1 名单与目的（上级、协作研发 / PM / 客服、导师）。
4. **试用期评估标准**：定硬指标（用 §3 能力维度）+ 软指标 + 中期反馈节点 + 转正结论选项（含不通过的合规处置路径）。

## 填好的范例（脱敏，承接 TTPOS Go 后端工程师 L3）

> 新同事 [占位]，入职 [日期]，试用期 6 个月，导师 [占位]，上级 [占位]，落在订单 / 桌台微服务线。

**首周关键项**：
- 配齐 GitHub / 飞书 / 服务器 / 数据库只读权限；本地用 `go mod tidy` 跑通主服务 + 连本地 MySQL/Redis；读懂 saas + `shop{uuid}` 多租户与事件总线规范。
- 与上级、对账 / 支付模块负责人、对接 PM 各 1:1；读 README 与领域术语（开台 / 转台 / 对账 / 堂食打包外送）。
- 完成首个 bugfix 并合入（走能过 ttpos-bot 质量门的 issue / PR 流程）。

**30-60-90**

| 阶段 | 可衡量目标 | 评估方式 |
|---|---|---|
| 30 天 | 跑通本地环境、熟悉订单 / 桌台代码与多租户约定，独立完成 ≥3 个中小需求 / bugfix 并合入 | 上级看 PR 质量 + 周会反馈 |
| 60 天 | 独立负责一个子模块迭代（如支付回调幂等 / 对账），主导一次小型技术方案评审 | 方案评审结论 + 线上无 P1 引入 |
| 90 天 | 独立 owner 一个交易子系统季度演进，季度 P1 故障 0 引入，能正确处理并发（业务键加锁）与一致性 | 转正评审据产出 + 故障 / APM 数据 |

**试用期转正评估标准**
- 硬指标（取 `hr-playbook.md` §3.1）：90 天内独立 owner 一个子模块、需求按期交付率 ≥ [目标]、无重大线上事故引入、并发 / 幂等 / 多租户处理正确。
- 软指标：code review 质量、在飞书 + GitHub 上写得清的协作、对线上质量与数据一致性的 owner 意识。
- 节点反馈：第 30、60 天各一次中期反馈（书面留痕）。
- 转正结论：转正 / 依规延长 / 不通过（依法处理，需送审）。

> Flutter 岗示意（同法换）：首周 `melos bootstrap` + `build_runner` 跑通某终端（如 pos / shop）；30 天熟悉 GetX / 分层 / 某终端，60 天独立负责一个页面 / 模块并补测试，90 天 owner 一个跨端复用组件且支付 / 订单路径测试达标。客服岗示意：30 天熟悉 POS 故障域与质量门、独立分诊常见故障；60 天独立处理升级并写合格 issue；90 天 FCR / CSAT 达 [目标] 并沉淀 KB。

## 自检清单（交付前）

- [ ] 工程师计划含上手真实技术栈（Go `go mod` / Flutter `melos`+`build_runner`）与餐饮 POS 领域
- [ ] 每阶段目标可衡量（有数字 / 明确判据，不是「熟悉业务」泛词）
- [ ] 硬指标取自 §3 对应岗位能力维度
- [ ] 含中期反馈节点（30/60）与书面留痕
- [ ] 含转正评估标准与不通过的合规路径
- [ ] 试用期不超法定上限、不二次约定
- [ ] 账号 / 仓库 / 服务器权限按需最小授予；新人个人信息脱敏

## 边界

- 个人信息脱敏；不给新人超范围的业务库 / 生产数据权限。
- 延长试用期或不通过须合规并经审批；相关通知 / 处置文件为草稿（需送审）。
- 试用期不得超法定上限、同一员工不得二次约定试用期。
