# 含胜任力模型的 JD（TTPOS 岗位）
## 输出纪律

回答从结果开始：先给结论、交付物、必要假设或需要用户补充的关键信息，再给细节。可以在内部读取 AGENTS、knowledge、templates 或 MCP 配置，但不要把内部过程写成用户可见开场。不要以“使用 `skill` / 我会按 / 我会先 / 我先读取 / 已确认”开头；除非用户明确要求解释过程或需要说明阻塞原因，否则不叙述工具调用和资产读取过程。


**产出物**：一份**具名 JD（含胜任力维度）+ 评估维度表**，可直接交用人经理评审、对外发布（草稿态）。岗位钉到 TTPOS 真实岗位族：Go 后端 / Flutter / PM / 客服。

## 前置输入（缺则先问，不臆造）

岗位族（Go 后端 / Flutter / PM / 客服）、目标职级与薪档、所属团队 / 汇报线、编制类型（新增 / 替补）、核心要解决的业务问题（落到 TTPOS 哪条线：订单 / 桌台 / 支付 / 对账 / 多租户 / 某终端 / 某市场）、必备 vs 加分、用人时间线、决策人与面试官。

## 引用资产

- 方法论：`knowledge/hr-playbook.md` §1（需求与画像、胜任力模型）、§2（JD 与渠道）、**§3 对应岗位的真实能力维度**（3.1 Go / 3.2 Flutter / 3.3 PM / 3.4 客服）。
- 骨架：`templates/jd.md`。
- 职级对标口径：`knowledge/benchmarks.md` §4（坊间、非官方）。
- 公司语境：`AGENTS.md`「公司语境 / 招聘对象」。

## 步骤

1. **需求对齐**：用 §1「编制对齐三问」确认是否该开、解决什么业务问题（落到 TTPOS 真实业务）、职级 / 预算 / 时间线 / 决策人。
2. **胜任力建模**：按 4 类维度（硬技能 / 问题解决 + 业务理解 / 协作沟通 / 价值观）写出**目标职级**的行为锚点；**硬技能维度直接取 §3 对应岗位的真实技术栈维度**（如 Go 并发 / GORM / 微服务；或 Flutter / GetX / Melos），确保每条可被面试证据验证。
3. **JD 撰写**：按 `templates/jd.md` 结构填写；技术栈写 TTPOS **真实在用的**（Gin/GORM/MySQL/Redis；Flutter/GetX/Dio/Freezed/Melos），核心职责 5–8 条动词开头可衡量；必备 vs 加分分开列；餐饮 POS 领域经验放加分而非必备。
4. **评估维度对齐**：把胜任力维度落进 JD「胜任力维度」表，供 `structured-interview-kit` 直接复用。

## 填好的范例（脱敏）

> 场景：TTPOS 中国团队**新增**一名 **Go 后端工程师**，目标职级「资深工程师（自建 L3，外部坊间对标 ≈ 阿里 P6+，非官方）」，落在交易 / 桌台微服务线，团队 6 人，汇报给后端负责人，时间线 6 周。

**岗位概述**：负责 TTPOS 餐饮收银核心微服务（订单 / 桌台 / 支付回调 / 对账）的设计、开发与线上稳定性，保障高峰营业期下单与结算的正确与高可用，支撑多租户（saas + 每店 `shop{uuid}` 库）与连锁场景。

**核心职责**
1. 负责订单 / 桌台 / 支付回调相关 Go 微服务（Gin + GORM）的设计、开发与线上稳定性，季度 P1 故障数 ≤ [目标]。
2. 主导一个核心子系统的演进（如对账 / 幂等支付回调 / 库存一致性），输出方案并落地。
3. 优化高峰期核心链路性能与并发安全（开台 / 转台用业务键加锁），核心接口 P99 延迟降至 [目标]。
4. 完善事件总线驱动的跨服务协作（下单 → 厨显 / 库存 / 会员），保障最终一致。
5. Code review 与工程规范沉淀（错误返回不 panic、单测覆盖支付 / 订单高风险路径），带 1–2 名初级工程师。

**任职要求**
- 必备：5 年以上 Go 后端经验；精通 Gin / GORM 或同类，熟 MySQL / Redis；有高并发 / 分布式与数据一致性实践；能独立负责子系统。
- 加分：支付 / 对账 / 交易系统经验；餐饮 / 零售 / POS / SaaS 行业经验；事件驱动 / gRPC / WebSocket 经验；开源贡献；带过人。

**胜任力维度（行为锚点，L3；硬技能取 `hr-playbook.md` §3.1）**

| 维度 | L3 行为锚点 |
|---|---|
| 硬技能（Go / Gin / GORM / 微服务） | 能独立设计并落地一个核心交易子系统，正确按业务键加锁、用事件总线解耦、防 N+1 与事务边界错误 |
| 问题解决 + 业务理解 | 能定位高峰期跨服务线上故障（如支付回调重复 / 缓存击穿）并给根因与幂等 / 补偿长期方案；懂多租户与对账口径 |
| 协作沟通 | 能在飞书 + GitHub 上推动需求拆解与排期，写得清的 issue / 方案，化解跨服务依赖阻塞 |
| 价值观匹配 | 对线上质量与数据一致性有 owner 意识，主动补位而非甩锅 |

**团队亮点**：真实高并发餐饮交易系统、技术自主权高、6 人小团队成长空间大、出海（中国 + 泰国）多市场场景。

> 其他岗位族示意（同法换维度）：**Flutter** 硬技能取 §3.2（Flutter / GetX 状态管理 / Dio+Freezed / Melos monorepo 分层 / 支付订单高风险模块测试）；**PM** 取 §3.3（餐饮 POS 业务 / 多租户出海 / 能过 ttpos-bot 质量门的 issue / sprint 节奏）；**客服** 取 §3.4（共情 / POS 故障分诊 / 工程化复述升级 / 飞书 + GitHub 工具流）。

## 自检清单（交付前）

- [ ] 岗位钉到 TTPOS 真实岗位族与业务线（非泛 HR / 泛互联网）
- [ ] 技术栈写真实在用的（Gin/GORM/MySQL/Redis 或 Flutter/GetX/Dio/Freezed/Melos），未堆时髦词
- [ ] 要求与目标职级匹配（没用高一级要求招低一级预算）
- [ ] 必备项克制且为可验证标准（非形容词），与加分项分开；领域 / 泰语 / 出海放加分
- [ ] 无歧视性 / 套话表述（不含与绩效无关的学历 / 年龄 / 性别硬门槛）
- [ ] 每个胜任力维度都能在面试中被证据验证（可交给 `structured-interview-kit`）
- [ ] 薪资用职级 / 分位口径，未写精确个人薪资

## 边界

- 个人信息与具体薪资脱敏。
- JD 为草稿，对外发布前经用人经理与 HR 负责人确认。
- 职级对标为坊间口径（非官方），仅作外部参考。
