# 机会评估（TTPOS 功能机会）
## 输出纪律

回答从结果开始：先给结论、交付物、必要假设或需要用户补充的关键信息，再给细节。可以在内部读取 AGENTS、knowledge、templates 或 MCP 配置，但不要把内部过程写成用户可见开场。不要以“使用 `skill` / 我会按 / 我会先 / 我先读取 / 已确认”开头；除非用户明确要求解释过程或需要说明阻塞原因，否则不叙述工具调用和资产读取过程。


## 产出物

一份《机会评估报告》，结论为 **Go / No-Go / 再验证** 三态之一（非只罗列信息），含门店 Job、经营规模、终端/竞品替代、多租户可行性、下一步。

## 前置输入

- 候选想法 / 客服升级的 GitHub issue / 经营数据异常 / HQ 诉求（往往是「方案」，需回溯 Job）。
- 可拿到的数据：门店数、客单价/翻台/退单等经营指标、竞品 POS 信息（拿不到标假设）。

## 引用资产

- 方法论：`knowledge/product-playbook.md` §1（门店角色×终端、JTBD、需求来源）。
- 口径：`knowledge/benchmarks.md` §5（TTPOS 经营指标 + 表 lineage）；RICE 锚点 §1（用于初判 Priority）。

## 步骤

1. **回溯 Job**：把想法翻成 Job Story，定位「谁/哪个终端/交易闭环哪一环」，区分问题与方案。
2. **业务目标对齐**：解决哪个经营目标？关联北极星 / 经营指标。
3. **经营规模与价值**：谁有这 Job、多频、多痛、影响多少门店/订单/金额；用经营数据或显式假设估，标来源。
4. **竞品 / 替代方案**：门店当前「雇佣」什么（含 Excel/人工/纸质/竞品 POS）；我们凭什么更好。
5. **可行性（多租户/终端）**：shop 库 or saas 库、新表、终端风险、HQ/连锁差异、市场差异的门槛与硬骨头。
6. **Go/No-Go/再验证**：三态结论 + 理由 + 下一步（Go→交 prd-writer；再验证→给验证设计）。

## 填好的范例（TTPOS · 桌台地图拖拽布局）

> 场景：店长反馈「桌台太多、新收银找不到桌、转台容易搞错」。现有 shop 端桌台是列表/网格，不直观。（真实仓库有任务 `story-admin-desktop-table-map`，新表 `ttpos_desk_map_layout`。）

**1. 回溯 Job**
`当 门店改桌位布局或新收银上手时，店长/收银 想要 在贴合真实店面的地图上看到桌台位置与开台状态，以便 快速找桌、准确开台/转台、减少出错。`
嘴上的「桌台地图」是方案；Job 是「降低找桌/转台认知成本、减少开错台」。方案空间：除可视化地图外，还含「按区域(DeskRegion)分组」「开台状态(Desk.status)实时上色」。

**2. 业务目标**：降低开台/转台操作耗时与错误率，间接牵引**翻台率**（北极星）。假设：地图化 → 开台更快/更准 → 翻台提升（待验证猜想）。

**3. 经营规模与价值**：桌台数 ≥30 的中大型店受益最大。假设受影响门店占比 <待埋点确认>；价值锚点 = 开台/转台 `duration_ms`（`ttpos_order_operation_duration`，source=pos/shop）下降 + 开错台导致的退单/改单减少（`ttpos_return_order`）。痛感中高（新人上手慢、高峰易错），场景高频（每单都开台）。

**4. 竞品 / 替代方案**：竞品部分 POS 有平面图编辑；门店当前替代 = 凭记忆 + 桌号牌（极依赖熟练度）。差异化：地图 + **区域分组 + 实时开台状态上色 + 与现有 Desk/Region 模型打通**（拖拽布局存 `desk_map_layout.LayoutJson`），不止静态图。

**5. 可行性（多租户/终端）**：
- 库：shop{company_uuid} 库，**新增表 `ttpos_desk_map_layout`**（region_uuid 唯一索引 + LayoutJson）→ 需 migration + 旧版本 app 兼容（旧端无地图降级回列表）。
- 终端：shop(编辑器，中) + pos(只读渲染+开台，**高风险**)；kiosk/mobile 暂不涉。
- 硬骨头：拖拽布局编辑器是大块（约 13 SP，estimateFit 会归零，难一次进 sprint，应拆「编辑器 / 只读渲染」两阶段）；HQ 连锁是否统一布局下发需澄清。
- 初步 Effort 偏大，无合规风险。

**6. 结论：Go（分阶段）**
先做 **pos 端只读地图渲染 + 区域分组 + 开台状态上色**（先给一线价值，风险可控），**非目标**：复杂拖拽编辑器放第二阶段。理由：Job 真实高频、与现有 Desk/Region 模型契合、有差异化；但整体 13 SP 放不下单 sprint，按 `backlog-prioritization` 会触发 `sprint_risk`，故**拆分**。下一步：交 `prd-writer` 写「只读渲染」PRD + 用 `backlog-prioritization` 排期。
若拿不到「找桌/转台耗时高」证据（duration_ms 无显著差异），降为**再验证**：先在 3 家大店埋点对比有图/无图开台耗时，再决策编辑器投入。

## 自检清单

- [ ] 想法回溯到门店 Job，定位了角色×终端×交易闭环环节，区分问题与方案。
- [ ] 规模/价值锚定**经营指标**（duration_ms/退单/翻台/客单），有出处；拿不到的标假设 + 验证方式。
- [ ] 覆盖竞品 / 非软件替代（人工/纸质/记忆），说清差异化。
- [ ] 可行性点出**多租户(库/migration)、终端风险、HQ/连锁、版本兼容**的真硬骨头（不只「能做」）。
- [ ] 结论是 Go/No-Go/再验证三态，含理由与下一步（大块需求给拆分建议）。

## 边界

- 不臆造门店规模 / 竞品事实 / 巡店结论；TAM 大饼不替代「真正会用的门店有多少」。
- 结论是建议，经营规模与 Effort/SP 需与数据团队/研发对齐。
