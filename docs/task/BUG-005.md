# BUG-005 aiw run waits for orchestrator.task.* but runtime emits orchestrator.finished

## Description

`apps/cli/src/commands/run.ts:60-79` waits for terminal events
`orchestrator.task.succeeded` / `.failed` / `.cancelled`. The current
runtime never emits any of those — `packages/core/src/worker/orchestrator/service.ts`
only emits `orchestrator.finished` (success) and `orchestrator.error`
(failure) on the bus. As a result, every `aiw run --message ...` blocks
until `--timeout-ms` (default 120s) and exits 124, even when the
orchestrator has fully completed and printed the assistant reply.

`docs/cli.md:59,65` documents the same wrong event names, so anyone
reading the manual is misled too.

The `gateway-client/subscriber.ts:107-124` already maps the correct
events to the gateway-side `agent.done` frame
(`orchestrator.finished → finishReason: 'stop'`,
`orchestrator.error → finishReason: 'error'`), so `aim chat` is
unaffected — only `aiw run` is broken.

This was discovered during the PLAN-017 smoke. It is **not** part of
PLAN-017 scope but is a real CLI defect that surfaces every dev run.

### Acceptance criteria

- `aiw run --message "<text>"` exits with code `0` when the
  orchestrator completes successfully (emits `orchestrator.finished`).
- `aiw run --message "<text>"` exits with code `1` when the
  orchestrator fails (emits `orchestrator.error`).
- A unit test exercises both paths with a stub bus.
- `docs/cli.md` event names match the runtime contract.
- No regression to `aim chat` (gateway-client subscriber unchanged).
- Timeout behaviour (exit 124) preserved when neither terminal event
  fires within `--timeout-ms`.
