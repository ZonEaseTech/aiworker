# BUG-047 Worker Admin no-token state renders raw auth errors

- **status**: completed
- **priority**: P2
- **owner**: Codex
- **createdAt**: 2026-05-02 20:39
- **discoveredAt**: 2026-05-02 20:21
- **completedAt**: 2026-05-03
- **plan**: PLAN-070

## Observed Behavior

Opening local Worker Admin without a bearer token served the SPA, but the UI
rendered raw API error JSON such as `{"code":"auth-failed","message":"missing
Authorization header"}` inside cards and repeatedly polled authenticated API
endpoints that returned 401.

There is also a documentation/code expectation mismatch: the Worker Admin auth
helper comments describe loopback dev API calls as token-optional, but the real
local API returned 401 without a bearer token.

Relevant code pointer:

- `apps/web/src/worker/lib/auth.ts` documents loopback dev as not needing a
  token, while real local validation required one.

## Expected Behavior

The no-token admin state should fail closed while giving the operator a clear
next step, such as reopening the tokenized admin URL from `worker serve
--open`, pasting a token into a local-only prompt, or following a documented CLI
command to print a short-lived admin URL.

## Reproduction

1. Start a local worker with Worker Admin enabled.
2. Open `/admin/` manually without a `#token=` bootstrap hash and with no
   stored session token.
3. Observe raw auth JSON and repeated 401 API calls instead of a clear locked
   state.

## Acceptance Criteria

1. Worker Admin renders a clear unauthenticated state when no token is
   available.
2. The unauthenticated state avoids repeated background polling that floods the
   server with 401s.
3. `worker serve` output and Web auth comments agree on whether loopback admin
   calls require a bearer token.
4. Tests cover the missing-token UI state.

## Plan

- **PLAN-070**: Worker Admin locked state without bearer token.
