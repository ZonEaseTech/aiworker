# BUG-006 Make reloadRuntime serialisation explicit (in-process mutex)

- **status**: pending
- **priority**: P3
- **owner**: (unassigned)
- **createdAt**: 2026-04-26 14:50

## Description

CLAUDE.md (and `docs/architecture.md` §"身份与配置自举") states the
hot-reload invariant: "reload 必须串行化（禁止并发），防止老版本晚到
覆盖新版本." The invariant is sound, but the current implementation
in `apps/api/src/modes/worker.ts:110 reloadRuntime` and the shared
`packages/core/src/worker/management/config.ts:159 applyConfigUpdate`
have **no explicit serialisation**. The constraint is held implicitly by:

1. `putConfig` optimistic lock (`ifMatch`) — rejects most concurrent
   PUTs at the storage layer.
2. "Application-level non-concurrency" — production today only has
   manual operators, who will not race themselves.

Both holds are weak now that PLAN-017 BUG-003 wired up the second
reload trigger path (gateway WS `config.put`), and the web SPA can
share the operator surface with `aim`. A narrow race is reachable:

```
T0: A applyConfigUpdate(ifMatch=1) → putConfig OK → stored=2 → enter reloadRuntime
T1: A awaiting hydrate
T2: C applyConfigUpdate(ifMatch=2) → putConfig OK → stored=3 → enter reloadRuntime
T3: C hydrate completes first → swap state.runtime = v3
T4: A hydrate completes  → swap state.runtime = v2  ← stale wins
```

Outcome: `state.runtime` briefly points at v2 instead of v3 until the
next reload corrects it; `previous.dispose()` order may also tear down
fresh runtime resources held by C.

### Why this is P3 (not P2)

- The optimistic lock blocks 99% of would-be races — both branches must
  be issued with **different** `ifMatch` values within hydrate-window
  (~ms-100ms). Manual operators do not produce such timing.
- No automation path currently writes config (no cron-triggered
  `config.put`, no webhook).
- Even when triggered, `state.runtime` self-heals on the next reload;
  there is no persistent corruption.

### Acceptance criteria

- `reloadRuntime` (or `applyConfigUpdate`) holds an in-process mutex /
  promise chain so that concurrent calls run serially.
- A unit test demonstrates the race: two simultaneous calls with
  artificially staggered `hydrate` resolutions; assert that the later
  caller's swap always lands after the earlier caller's `dispose`.
- CLAUDE.md / `docs/architecture.md` updated: the invariant moves from
  "由应用层不并发维持" to "由 reloadRuntime 内部 mutex 强制保证."
- changelog entry; previous "待跟进" footnote (changelog line ~46) is
  removed.
- No new abstraction beyond a ~15-LOC mutex helper. Do not introduce a
  generic locking framework.

## Notes

- **Promote to P2** when any automated path that issues `config.put`
  lands (cron-driven config rotation, automated provisioning script,
  multi-tenant operator dashboard).
- Suggested implementation: a single `Promise<void>` chained inside
  `bootstrapWorkerApp` closure; `reloadRuntime` returns
  `lastReload = lastReload.then(() => doReload(...))`. Avoids any
  external dependency.
