# BUG-016 web channel webhook 无验签无鉴权（envelope 注入）

- **status**: resolved
- **priority**: P0（安全漏洞）
- **owner**: bkd/ug0x96ol

- **resolvedAt**: 2026-04-27 13:30

## Description

`packages/core/src/worker/channels/adapters/web.ts:50-54` 的 `webAdapter.verify()` 是空函数，注释自称 "trusted internal"。但 `apps/api/src/modes/worker.ts:166-168` 通过 `app.route('/', buildChannelRoutes(...))` 把 `/:channel/webhook` 挂在根，**不经 bearer auth**。

后果：任何能访问 worker 端口的攻击者都可以 `POST /web/webhook` 注入伪造 envelope，触发 orchestrator → LLM 调用 + 写入 `worker.db.messages`。worker 端口在内网通常无防护，公网部署时即便 Caddy 反代叠了 basic-auth（BUG-007），其他 channel 路径仍然预期开放给平台 webhook，因此把 `/web/webhook` 一并裸露。

### 攻击面

```bash
curl -X POST http://worker:8080/web/webhook \
     -H 'content-type: application/json' \
     -d '{"chatId":"target","text":"<注入 prompt>","userId":"any"}'
```

→ orchestrator 接受 envelope → 拉 LLM → 计费 / 数据写入 / 在已绑定 brain 中污染历史。

## Acceptance criteria

1. `webAdapter.verify()` 校验 `Authorization: Bearer <inboundToken>` 头，使用 `timingSafeEqualStrings` 常量时间比对。
2. binding 缺 `inboundToken`（含 undefined / 空串）时 verify 必须 throw → channel 路由返回 401。fail-closed。
3. `inboundToken` 走 secrets vault：`enumerateSecretPaths` / `redactSecrets` / `hydrateSecrets` 三处都覆盖。
4. zod schema 接受 `inboundToken?: string`；旧 redacted config 经 `putConfig` round-trip 不会丢值（empty = 保留）。
5. dashboard 配置面板暴露 `inboundToken` 字段 + Generate 按钮（运维一键生成）。
6. 新增单元测试覆盖 verify 的 4 种路径：valid token / invalid token / missing header / binding 无 token。
7. `bun run typecheck` + 相关 vitest/bun:test 全绿。

## Investigation

### 接入点

- 入口路由：`apps/api/src/worker/channels/routes.ts:31-54`
  - 已经在调 `await adapter.verify(rawBody, headers, binding)`，throw → 401。
  - 已把 `headers` 全小写化，可直接读 `headers.authorization`。
- 类型：`packages/shared/src/fleet/channel.ts:5-22` 的 discriminated union；`{ channel: 'web' }` 是其中一支。
- zod schema：`packages/core/src/worker/management/config-schema.ts:84-93`，需要把 `inboundToken: z.string().optional()` 加进 web 分支。
- secret 管道：`packages/core/src/worker/config/secret-paths.ts` 的 `enumerateSecretPaths` / `redactSecrets` / `hydrateSecrets` 三函数；当前 web 分支都是空 `break` / 直接返回。
- 比对工具：`packages/core/src/worker/secrets/crypto.ts::timingSafeEqualStrings`（已 export 到 `@zonease/aiworker-core`）。
- 现成参照：`packages/core/src/worker/channels/adapters/telegram.ts:117-126` —— 有 secret 才校验 + `timingSafeStringEqual`。本 BUG 与之差异是 fail-closed（无 secret 时拒绝）。

### Empty-string round-trip 语义

`packages/core/src/worker/management/config.ts:90-94` 已经实现 "empty 表示不重写"。新加的 `inboundToken` 沿用这个语义即可：

- 用户输入空 → `enumerateSecretPaths` 跳过该 path → vault 不动；
- 用户输入新值 → vault 覆写；
- redacted view 永远是 `''`，dashboard 看不到原值。

### Backward compatibility

- 旧的 `worker_config.configJson` 里 `{ channel: 'web' }` 没有 `inboundToken` 字段。读上来 `inboundToken === undefined` → verify fail-closed → 旧部署的 web channel ingest 立即拒绝。这是预期：旧路径就是漏洞，运维必须上 dashboard 设一次 token 才能恢复。
- `info.test.ts` / `channel-test.test.ts` / `web.test.ts` 中已存在的 `{ channel: 'web' }` 测试 fixture **类型上仍合法**（inboundToken 是 optional），但凡走 verify 的新测试需要显式传 token。

### Dashboard / 客户端调用方

grep 现有源码：没有任何前端 / 后端代码主动 `POST /web/webhook`。这是一个为外部客户端预留的 ingress，目前无 in-tree 调用方。修复后需要的 web 客户端（dashboard chat widget 等）必须显式带 `Authorization: Bearer <inboundToken>`，由运维通过 dashboard 拷贝。

## Proposal（方案 A）

采纳 issue 描述中的方案 A。理由：

- 与 Telegram 的 `webhookSecretToken` 形态对齐（同样是平台 webhook 时的额外秘密），mental model 统一。
- 不污染 `apps/api`：仍然是 adapter 层的职责，符合 "channel adapter 自管验签" 不变量。
- 方案 B 把 `web` 在 router 层特判，与 "router 不依赖 channel-specific 分支" 原则相悖。

8. `docs/changelog.md` 写一笔，task 文件标 resolved。
