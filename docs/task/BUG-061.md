# BUG-061 `aiworker brain admission show/list` claims `redacted: true` but returns plaintext secrets

- **status**: completed
- **priority**: P1
- **owner**: aiworker-maintainer

- **relatesTo**: BUG-055 (admission apply secret-scan), PLAN-103 (Admission MVP)

## Observed Behavior

Inject an admission proposal whose `payload.body` contains a secret-like string (`apiKey=sk-LIVE-shouldnotpersist`):

```bash
aiworker brain admission propose --i-know-this-is-debug \
  --id prop-qa-secret --kind memory-add --target memories/qa-secret-in-body \
  --soul developer --evidence ev.json --payload payload.json
# payload.json: {"body":"# leak test\n\napiKey=sk-LIVE-shouldnotpersist\nbearer=eyJabc",...}
```

`aiworker brain admission show prop-qa-secret` returns:

```json
{
  "redacted": true,
  "proposal": {
    "payload": {
      "body": "# leak test\n\napiKey=sk-LIVE-shouldnotpersist\nbearer=eyJabc"
    }
  }
}
```

The `redacted: true` claim is **false**. `payload.body` returns the plaintext secret unmodified. Same on `aiworker brain admission list` (default `redacted=true`) and on the REST endpoint `/api/worker/brain/admission/<id>`.

`--show-sensitive` flips `redacted` to `false` but the content is identical — the flag is functionally no-op for this case.

## Why BUG-055 fix is incomplete

BUG-055 was fixed in 0.7.0 for the **apply path**: `aiworker brain admission apply --commit` defaults to `--allow-secret-body block` and successfully blocks `sk-token` secrets from landing on disk. Reproduction of `apply prop-qa-secret --commit` returns `kind: blocked-by-secret-scan` with `secretScan.hits: [{rule:"sk-token", ...}]` ✓.

But the **read path** (list / show) never runs the same scanner. So:

- the secret never lands on disk (good)
- the secret is queryable forever via the worker REST API as long as the proposal exists in worker.db (bad)

## Impact

- Admin UI / Fleet UI typically calls `/api/worker/brain/admission` to render proposal cards; `redacted: true` UI badge shows but the underlying string is plaintext
- Operators with low-permission worker token would see the secret string while believing they were viewing a redacted view
- The `--show-sensitive` flag exists but is functionally no-op, fooling reviewers into thinking permissions matter

## Expected Behavior

Reuse the same `secretScan` policy that admission apply applies:

- Default (`redacted=true` / no `--show-sensitive`): scan all string-valued fields in `proposal` (payload.body, payload.indexEntry, summary, rollback, evidence values). Replace each hit with `[REDACTED:<rule>]`. Annotate `proposal.payload.body` with leading `# WARNING: sensitive content redacted` if any redaction occurred.
- `--show-sensitive=true` AND require explicit env (`AIWORKER_ADMIN_REVEAL=1`) or extra confirmation step: return raw payload.

## Validation

After fix, default `aiworker brain admission show <id>` and `/api/worker/brain/admission/<id>` must replace `sk-LIVE-shouldnotpersist` with `[REDACTED:sk-token]` (or equivalent), and `--show-sensitive` must require explicit secondary confirmation.
