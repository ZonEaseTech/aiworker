admission negative-path invariants:

## Negative-Path Evidence Highlights

| Check | developer-codex | general-assistant-claude-code |
|---|---|---|
| admission reject path | PASS (propose=0, reject=0, status=rejected, decisions=rejected, no memory file) | PASS (propose=0, reject=0, status=rejected, decisions=rejected, no memory file) |
| admission secret-scan-block path | PASS (apply=1, outcome.kind=blocked-by-secret-scan, status=approved, decisions=approved, no applied decision, no memory file) | PASS (apply=1, outcome.kind=blocked-by-secret-scan, status=approved, decisions=approved, no applied decision, no memory file) |

Together these checks prove the **negative** Project Brain governance
transitions:

- `pending → rejected`: the operator-driven reject CLI flips proposal status
  to `rejected`, writes a `decision='rejected'` row, and never produces a
  canonical memory file.
- `approved → blocked-by-secret-scan` (BUG-055 regression line): a body
  matching `scanBodyForSecrets` is refused at the materializer; the proposal
  stays `approved`, no `'applied'` decision row is written, and no canonical
  memory file leaks. The CLI exits with code 1 alongside the diagnostic JSON,
  which the harness pins via assertion.

The first run of the new blocks (`qa-2026-05-06-governance-rejects`) failed
the secret-scan-block assertion because the assertion expected exit 0;
inspection revealed the product correctly returns exit 1 alongside
`outcome.kind='blocked-by-secret-scan'`. The harness was updated to require
exit 1 plus the parsed outcome JSON, and this `r2` rerun passed for both
pairs.

The existing 36 pre-PLAN-129 checks (init, executor doctor, six LLM turns,
direct propose/approve/apply, MEMORY.md index, brain brief projection, chat
continuity, decision truthfulness, tool-call observability, risk policy,
admission claim vs DB, REST/SSE smoke, Worker Admin mount) continue to PASS
for both pairs.
