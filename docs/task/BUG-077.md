# BUG-077 Codex multi-tool turns abort with dead-loop-suspected after legitimate tool activity

## Observed Behavior

The current 0.9.0 local-worker matrix produced four non-zero Codex turns across
three Souls. Each failed with the same orchestrator abort:

```text
dead-loop-suspected:tool_call=8,no_text_delta
```

Affected turns:

- `raw/hr-recruiting-codex/turn08.stdout` and `.stderr`
- `raw/hr-recruiting-codex/turn12.stdout` and `.stderr`
- `raw/finance-ops-codex/turn12.stdout` and `.stderr`
- `raw/qa-reviewer-codex/turn12.stdout` and `.stderr`

The raw streams show legitimate tool activity such as `aiworker brain
admission propose`, `aiworker brain admission show`, and file reads. In at
least one case the admission proposal was successfully created immediately
before the abort event, but the turn still ended as `orchestrator.aborted` and
`orchestrator.error`.

Sanitized summary:

- `/home/ben/projects/debug-aiworker-cx/release-0.9.0-governance/sanitized/matrix-summary.md`
- `/home/ben/projects/debug-aiworker-cx/release-0.9.0-governance/reports/summary.json`

## Expected Behavior

The loop guard should stop real executor dead loops without killing normal
multi-tool workflows that are still making progress. A successful tool call
that changes state or provides evidence should either reset the guard or allow
the executor to produce a final answer.

## Actual Behavior

Codex turns can be aborted after a fixed pattern of tool calls even when the
tool calls are legitimate, bounded, and successful. This leaves the worker in a
partially useful state: files or admission rows may exist, but the user-facing
turn exits non-zero and has no clean final answer.

## Risk

P2. This is not as severe as a governance boundary violation, but it damages
"跑顺" for real Codex-backed worker use and makes longer evidence-gathering or
admission workflows unreliable.

```sh
cat "$RUN/raw/hr-recruiting-codex/turn08.stderr"
```

## Validation

After fix:

1. The same prompt can complete with a final answer after successful tool
   progress.
2. True no-progress loops are still aborted.
3. Abort telemetry distinguishes fixed threshold exhaustion from real repeated
   identical tool calls.

- Dead-loop tracking now treats `tool_result` and terminal tool lifecycle
  statuses as progress while preserving abort behavior for repeated tool calls
  without text or results.
