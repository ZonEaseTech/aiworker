# BUG-070 codex executor emits no `orchestrator.tool_call` events — observability badly degraded vs claude-code

## DOC-006 framing

This supersedes BUG-050 and remains the canonical Codex tool-call observability
task. Post-DOC-005, tool-call events are needed for audit, approval, and
operator trust; they are not a reason for Brain Kernel to own executor tool
policy or sandbox semantics.

## Observed Behavior

In 0.8.0 release validation the same multi-turn matrix was run against
`claude-code/default` and `codex/default` engines. For every turn that
involved tool use (file writes, shell, CLI invocation) the event streams
look very different:

claude-code engine, dev-claude-code turn 1 (subset):

```
orchestrator.tool_call name=Write   file_path=.../memory/project_marker.md
orchestrator.tool_call name=Read    file_path=.../memory/MEMORY.md
orchestrator.tool_call name=Write   file_path=.../memory/MEMORY.md
orchestrator.text     delta="**Soul**：Developer..."
```

codex engine, finance turn 7 (subset):

```
orchestrator.text     delta="..."
orchestrator.text     delta="..."
orchestrator.finished
```

For `finance/turn07` the codex executor really did execute a file write
(`.aiworker/local/admission/monthly-reconciliation-raw-detail-retention.payload.json`),
a `brain admission propose` CLI invocation, and follow-up reads — yet the
AIWorker event stream did not surface a single `orchestrator.tool_call`
event. The only structured signals were `orchestrator.text` deltas and
`orchestrator.finished`.

Across all 12 turns × 2 codex Souls the event stream contained zero
`orchestrator.tool_call` payloads.

## Why this matters

- Worker Admin, Fleet UI, gateway audit, CLI logs, and any third-party
  observability built on AIWorker events lose codex tool-call visibility
  entirely. Operators see "the model wrote some text" with no record of
  which files it touched or which CLI it invoked.
- Cross-engine policy enforcement breaks: any future feature that wants to
  inspect, gate, or audit tool calls (capability decision, sandbox policy,
  approval gating, redaction) becomes engine-specific.
- The mismatch hides genuine bugs. BUG-068's "claude-code does not trigger
  admission" was easy to spot via tool calls; the symmetric "codex did
  trigger admission" was only discoverable by inspecting `worker.db`.

## Root Cause Hint

The codex adapter in `packages/core/src/worker/...` likely consumes codex's
chunked output but only forwards assistant text deltas to the orchestrator
event bus. Codex's tool-call frames (function calls or shell exec records)
are dropped instead of being mapped to `orchestrator.tool_call`.

## Reproduction

Same matrix as BUG-068. Compare:

```bash
grep -c '"type":"orchestrator.tool_call"' \
  /home/ben/projects/debug-aiworker/release-0.8.0/logs/dev-claude-code-turn*.log
# > 0 across the matrix

grep -c '"type":"orchestrator.tool_call"' \
  /home/ben/projects/debug-aiworker/release-0.8.0/logs/dev-codex-turn*.log
# 0 across the matrix
```

## Expected Behavior

Every executor adapter normalises tool calls into the same
`orchestrator.tool_call` envelope. At minimum the envelope should carry:

- engine identifier
- tool name (codex shell vs codex builtin vs MCP tool)
- arguments / command (subject to redaction policy)
- correlation id linking `tool_call` and `tool_result`

If codex genuinely cannot expose tool-level granularity for some streams,
the adapter should emit a coarser `orchestrator.tool_step` event with a
documented reason, rather than swallowing the information silently.

## Acceptance Criteria

1. Running the BUG-068 reproduction script on `codex/default` yields
   `orchestrator.tool_call` events for the proposed CLI invocation and any
   file writes performed by codex.
2. `worker.db` event count and event-stream count agree on tool-call usage
   per turn.
3. A focused codex-adapter test asserts the adapter forwards tool-call
   frames into the orchestrator bus.
4. Documentation lists the adapter's current granularity limitations
   (e.g. "codex shell exec is reported as a single `tool_call` with the
   command as argument") so consumers know what to expect.
