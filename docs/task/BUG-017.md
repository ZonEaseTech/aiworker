# BUG-017 Lark verificationToken + WhatsApp verifyToken 非常量时间比较

- **status**: completed

## Description

CLAUDE.md 关键不变量 "bearer / 共享 token 比较一律 `timingSafeEqualStrings`"
被两处 webhook 验证路径违反：

1. `packages/core/src/worker/channels/adapters/lark.ts:161`

   ```ts
   if (token === undefined || token !== binding.credentials.verificationToken)
     throw new Error('invalid Lark verification token')
   ```

   普通 `!==`。Lark 未加密路径**只**靠这个 token 验证 webhook 真伪
   （加密路径还有 AES + token 双层），一旦推算出 token 即可伪造事件。

2. `apps/api/src/worker/channels/routes.ts:26`

   ```ts
   if (mode === 'subscribe' && token === binding.credentials.verifyToken)
     return c.text(challenge, 200)
   ```

   普通 `===`。WhatsApp Cloud API 的 `GET /webhook` 订阅挑战。
   推算成功后可冒充 Meta 完成订阅劫持，把 webhook 重定向到攻击者
   主机。POST 仍有 `X-Hub-Signature-256` HMAC 兜底，所以风险次于 Lark。

## 风险

- **Lark**：跨网时序攻击者基于响应耗时差推算 `verificationToken` →
  伪造 Lark 事件、注入虚假用户消息。
- **WhatsApp**：推算 `verifyToken` 后可在 Meta 控制台层完成订阅劫持，
  间接劫持后续 webhook 交付。

## 修复方案

两处都改成 `timingSafeEqualStrings(actual, expected)`：

- core 内部：`packages/core/src/worker/channels/adapters/lark.ts`
  从 `../../secrets/crypto` 引入。
- apps/api 跨包：`@zonease/aiworker-core` 已 re-export
  `timingSafeEqualStrings`（见 `packages/core/src/index.ts:92`），
  与 `apps/api/src/worker/management/bearer-auth.ts:2` 保持同款引用。

  - 增补「同长度但内容不同」case，覆盖 timing-safe 路径

  - WhatsApp `GET /whatsapp/webhook`：
    - 正确 token + `hub.mode=subscribe` → 200 + challenge 文本回显
    - 错误同长度 token → 403 forbidden
    - 错误不同长度 token → 403 forbidden
    - 错误 `hub.mode` → 403 forbidden
    - 未绑定 whatsapp channel → 404
