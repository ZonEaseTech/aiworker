# BUG-069 codex executor session continuity is broken — same chat-id splits into multiple conversations, marker recall fails

- **status**: completed
- **priority**: P1
- **owner**: Codex
- **createdAt**: 2026-05-05 14:13
- **discoveredAt**: 2026-05-05 13:59
- **relatesTo**: BUG-052 (claude-code streaming), AGENTS.md "Project Brain comes first"

## DOC-006 framing

This remains a P1 executor parity defect. Post-DOC-005, the goal is not to
move continuity into Brain hard logic; the codex adapter must preserve or
replay conversation context so Project Brain projection and chat-id semantics
behave consistently across supported executors.

## Observed Behavior

During 0.8.0 release validation, two Souls used `codex/default` as executor
engine and ran 12-turn chats under a single `--chat-id`. Final state in
`worker.db`:

| Soul       | conversations | messages | comment |
|------------|---------------|----------|---------|
| dev-codex  | 7             | 24       | same `chat_id=multi-turn-dev-cx` split into 7 conversations |
| finance    | 6             | 24       | same `chat_id=multi-turn-fin-1` split into 6 conversations |

By contrast, claude-code Souls under the same harness:

| Soul             | conversations | messages | comment |
|------------------|---------------|----------|---------|
| dev-claude-code  | 1             | 24       | same chat-id, single conversation, full continuity |
| hr               | 1             | 24       | same |
| qa               | 1             | 24       | same |

`aiworker sessions list` for `dev-codex` reports the **last-created**
conversation as `currentConversationId`, so prior turns' history is no longer
the active conversation context.

Effect on continuity: in the dev-codex matrix, turn 1 stored
`MARKER_DEV_CODEX_T1=bravo-5108` and turn 4 was asked to recall it. The
LLM's reply (extracted from `dev-codex-turn04.log`):

> 我会先查本地记忆索引里是否有 marker 相关记录；如果没有命中，我会明确说明
> 当前上下文里没有这个事实。记忆索引没有直接写出名字和值，只命中了几条
> aiworker 会话验证记录。

→ marker recall **failed**. The same prompt on claude-code returned
`MARKER_DEV_CC_T1=alpha-7392` precisely.

## Root Cause Hint

Likely a missing `--continue` / `--resume` invocation when the codex adapter
spawns the codex CLI for a non-first turn under an existing `chat_id`. Codex
without a resume flag starts a fresh conversation each invocation.

`packages/core/src/worker/orchestrator/runtime/...` (or the codex adapter
under `apps/cli` / `packages/core`) likely needs to:

1. Look up the active session for the incoming `chat_id`.
2. If a prior conversation exists, pass codex's session-resume identifier so
   the new turn lands in the same conversation.
3. Or, if codex cannot truly resume across processes, append the prior
   conversation transcript into the new prompt as conversation history before
   invoking codex.

Either approach must end with a single AIWorker conversation per chat-id.

## Why this matters

- Multi-turn coherence is the central premise of Project Brain. If chat-id
  alone does not guarantee continuity on codex, every codex-backed Soul
  silently loses memory across turn boundaries even though the operator
  thinks they are talking to a single agent.
- Cross-engine portability promise breaks: the same Soul behaves
  differently depending on executor selection. Operators choosing codex over
  claude-code (e.g. for cost or compliance reasons) get a degraded product.
- Downstream features that assume one conversation per chat (sessions
  listing, transcript replay, audit trails, fleet UI threading) over-count
  conversations and under-count messages per session.

## Expected Behavior

A single AIWorker conversation per `chat_id` regardless of executor engine.
The exact mechanism (codex resume flag vs. AIWorker-side prompt assembly) is
an implementation detail; the contract is that
`SELECT count(*) FROM conversations WHERE chat_id=?` is `1` after N turns.

## Acceptance Criteria

1. After 5 sequential `aiworker run --chat-id <id>` calls on `codex/default`,
   `conversations` table has exactly 1 row for that chat-id.
2. `aiworker sessions list` reports the same conversation across turns
   (currentConversationId stable), and `aiworker sessions show <key>` shows
   accumulating message count, not a fresh count of 1.
3. A multi-turn marker-recall regression test on `codex/default` passes
   (turn 4 recalls the marker stored on turn 1).
4. Existing claude-code behaviour stays unchanged (single conversation per
   chat-id, regression covered).
