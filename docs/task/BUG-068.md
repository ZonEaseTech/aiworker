# BUG-068 Brain admission proposal pipeline has no LLM-discoverable entry-point — Souls running on claude-code engine never trigger AIWorker admission

- **status**: pending
- **priority**: P1
- **owner**:

- **discoveredAt**: 2026-05-05 14:00

## Observed Behavior

Across 5 Souls × 12 turns each (60 turns total) of 0.8.0 release validation,
every prompt explicitly asked the LLM to "submit this as a brain admission
proposal and tell me how to approve it". Final state of `brain_admission_proposals` table per Soul:

| Soul × Engine               | `.aiworker/memories/` files | DB admission rows | Claude Code user-level memory files |
|-----------------------------|-----------------------------|-------------------|-------------------------------------|
| dev-claude-code × claude-code | 0                         | 0                 | 3 (`MEMORY.md`, `project_marker.md`, `project_testing_convention.md`) |
| dev-codex × codex           | 0                           | **1** (`dev-codex-vitest-src-test-policy`) | 0 |
| hr × claude-code            | 0                           | 0                 | 2 (`MEMORY.md`, `project_hiring_policy_bgcheck.md`) |
| finance × codex             | 0                           | **1** (`monthly-reconciliation-raw-detail-retention`) | 0 |
| qa × claude-code            | 0                           | 0                 | 3 (`MEMORY.md`, `project_marker_qa_t1.md`, `feedback_p0_defect_admission.md`) |

Engine-conditional outcome:

- **claude-code engine: 0/3 Souls triggered AIWorker admission**. The LLM
  consistently chose its own user-level memory system (`~/.claude/projects/.../memory/`),
  wrote `MEMORY.md` + topic files there, and reported "已持久化到 memory /
  proposal 已采纳" to the user. Operator-side `aiworker brain admission list`
  remained empty.
- **codex engine: 2/2 Souls triggered AIWorker admission DB writes**. The LLM
  searched the CLI surface, discovered `aiworker brain admission propose`,
  and submitted real `memory-add` proposals. (See finance turn 7 log for the
  successful path.)

QA Soul user-level memory contains a particularly telling artefact: a
`feedback_p0_defect_admission.md` file with frontmatter
`status: proposal, proposed_by: user` — the LLM was clearly *trying* to model
admission semantics, but did so in the wrong storage backend.

## Root Cause Hint

Two compounding issues:

1. **`SOUL.md` / `AGENT.md` do not teach the LLM about AIWorker brain
   admission.** They describe the Soul's responsibilities and boundaries but
   never mention `aiworker brain admission propose`, the `.aiworker/memories/`
   layout, or the difference between AIWorker brain memory and the executor
   engine's native memory system.
2. **`brain admission propose` is a CLI command, not a tool exposed to the
   LLM.** Even when an executor (codex) enumerates CLI commands and discovers
   it, the schema is strict (`evidence kind` enum, kebab-case `--id`,
   six required fields) and the help banner labels the command "TODO-009
   调试入口：直接构造一条 admission proposal（仅供 fixture / 演示）", which
   discourages production use.

The combination means: on engines with strong native memory (claude-code), the
LLM happily uses the engine's memory; on engines without (codex), the LLM
reaches for AIWorker but only because there is no easier path.

## Why this matters

- Project Brain admission is the *only* sanctioned write path for
  long-lived memory under the Soul → admission → operator approval → apply
  flow. If the LLM cannot reach it, the entire Brain governance model is
  bypassed, and the operator gets no audit, no approval, no rollback hook.
- The bypass is silent and engine-specific. Operators on claude-code see
  "everything looks normal" while their AIWorker scope's brain memory remains
  empty and all real long-lived memory leaks into a per-user, per-project
  Claude Code directory that is *not* under AIWorker secret/scope governance.
- Cross-engine correctness is broken: the same Soul, same prompt, same user
  intent yields a populated admission queue on codex and zero records on
  claude-code.

## Expected Behavior

1. `SOUL.md` / `AGENT.md` injected into the LLM prompt must explicitly direct
   the LLM to use AIWorker brain admission for any long-lived memory or
   policy proposal, with examples of the CLI invocation or — better — the
   tool surface.
2. Brain admission propose should be exposed to the LLM as a structured tool
   (MCP tool, executor builtin, or skill) with a non-debug status, not only
   as a CLI command tagged "调试入口". The `--i-know-this-is-debug` gate
   discourages exactly the production path Souls need.
3. The runtime should detect the "LLM wrote to engine-native memory while
   AIWorker brain admission stayed empty" pattern (e.g. claude-code's
   `~/.claude/projects/<scope>/memory/MEMORY.md` updated within an `aiworker
   run`) and surface a `brain.governance.bypass` warning event.

## Acceptance Criteria

1. With `claude-code` engine, the same prompt-set that submits an admission
   on `codex` produces an admission proposal in `brain_admission_proposals`
   with no other change.
2. AGENT.md / SOUL.md template adjusted (or runtime injection added) so the
   LLM is told what to do when asked to "remember X long-term".
3. Either `brain admission propose` is promoted from debug-only to
   production-supported, or a parallel LLM-facing tool wraps it.
4. End-to-end test: a 2-turn fixture asks for long-term memory and asserts
   `brain_admission_proposals` count increases by 1 on both engines.
