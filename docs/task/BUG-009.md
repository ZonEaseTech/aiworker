# BUG-009 OTP approve does not upgrade ws to NodeRegistry

## Description

PLAN-019 / FEAT-026 AC #4 demands:

> `aim enroll approve <otp>` writes fleet.db row with `addedBy='otp'`
> and pushes deviceToken back to the waiting worker via the same WS
> connection; **worker upgrades from `node-pending` to `node`**.

The first half is done — fleet row + `enrollment.approved` event are
both written/pushed. **The second half is missing**:

- `apps/gateway/src/router/methods/enroll.ts::handleEnrollApprove`
  comment line 15-18 explicitly defers the NodeRegistry upgrade to S3.
- `apps/gateway/src/server.ts` only handles `node-pending` in the
  connect-frame and close paths; it never reacts to "approve happened
  on this `node-pending` ws".
- Result: after a successful `aim enroll approve`, the ws stays in
  `role='node-pending'` forever; `NodeRegistry.has(workerId) === false`;
  `aim workers list` reports `online: false`; any `chat.send` /
  `config.put` forwarded to this worker would 404 with `node_offline`.

Reproduced live during PLAN-019 e2e (workstation OTP-mode worker
`w_wzg6kzsr0hey` joined fleet via `AMWB-9GAD`, fleet row exists with
`addedBy='otp'`, worker stdout shows `approved as ...; deviceToken=...`,
but `aim workers list` returns `online: false`).

### Acceptance criteria

1. After `aim enroll approve`, `aim workers list` shows the new worker
   as `online: true`.
2. The pending ws is registered in `NodeRegistry` under the approved
   `workerId`, with `role='node'` (no longer `'node-pending'`).
3. Gateway broadcasts `worker.online` event to all operators.
4. If a stale node connection for the same `workerId` already exists,
   it is replaced (close 1012 `replaced_by_enroll_approve`), matching
   the connect-path behaviour in `server.ts` line 306-313.
5. `aim chat <newWorkerId> '...'` is dispatched (not blocked by
   `node_offline`).
6. Existing `enroll-otp.test.ts` happy-path case is extended to assert
   the post-approve ws is in `NodeRegistry`.
7. `connect.accepted` audit is **not** re-written (audit volume); the
   `gateway.enrollment.approved` audit already covers the join.
