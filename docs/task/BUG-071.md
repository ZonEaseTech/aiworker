# BUG-071 `aiworker executor doctor` prints contradictory banner: header says "0 ERR · 0 WARN" but body says `Status: WARN`

- **status**: completed
- **priority**: P2
- **owner**: Codex
- **createdAt**: 2026-05-05 14:14
- **discoveredAt**: 2026-05-05 13:55

## DOC-006 framing

This remains a post-decision operator trust defect. Doctor output is part of
the same truthfulness contract as Brain decision events: status banners and
section state must describe the actual PASS/WARN/INFO semantics without
contradiction.

## Observed Behavior

After a fresh `aiworker init` + `aiworker executor select --engine claude-code --apply`,
running `aiworker executor doctor --engine claude-code` prints:

```
[aiworker executor doctor] OK — 1 engine; 0 ERR · 0 WARN (fresh-init defaults; overlay declarations are optional)
[aiworker executor doctor] project executor overlay validation
Root  : .../.aiworker
File  : .../.aiworker/executor-capabilities.json
Status: WARN
  PASS    configured task executor: claude-code/default (config v2)
  PASS    declared project executor overlay entries: 0 (fresh-init default; declare an overlay only when project pins MCP / config)
  PASS    claude-code binary likely ready (cli: claude, overlay mcp: 0)
  INFO    claude-code ambient runtime: user/host MCP, skills, plugins, auth and native sessions live outside AIWorker
  INFO    engine login/auth state is managed by each engine CLI; AIWorker does not probe it
```

The top banner says **0 WARN**. The body says **Status: WARN**. Both lines
come from the same command on the same input.

Reproduced on every Soul in 0.8.0 release validation (5/5).

## Why this matters

- Operators copy banner output into runbooks, deployment audits, and
  onboarding docs. A self-contradicting banner makes the doctor output
  ambiguous to humans and to any CI grep that keys on "0 WARN".
- Casts doubt on the rest of the doctor output — if WARN/clean state are
  inconsistent here, what else is wrong?

## Root Cause Hint

Two summary functions probably compute the count differently:

1. The header counts only fatal/blocking conditions; "fresh-init default
   overlay" doesn't count.
2. The per-section status uses a stricter rubric where any non-PASS row
   (the two `INFO` lines) bumps the section to WARN.

Either harmonise the counts or relabel the sections so banner and body tell
the same story.

## Expected Behavior

The header banner reflects the same WARN/PASS semantics as the per-section
`Status:` line. A clean fresh-init system should print:

```
[aiworker executor doctor] OK — 1 engine; 0 ERR · 0 WARN
Status: PASS
```

Or, if the underlying state is "PASS with informational notes", both rows
should agree on PASS and the INFO entries should not bump section status.

## Acceptance Criteria

1. Banner counters and per-section `Status:` agree on a single rubric.
2. Docs (`docs/architecture.md` or `docs/executor-engines.md`) state
   what triggers WARN vs PASS.
3. A focused snapshot test pins the doctor output of a fresh-init project so
   the contradiction cannot regress silently.
