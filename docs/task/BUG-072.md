# BUG-072 `aiworker init` prints bootstrap token + master-key to stdout with weak warning UX, easy to leak into logs / shared screenshots

- **status**: pending
- **priority**: P2
- **owner**:
- **createdAt**: 2026-05-05 14:15
- **discoveredAt**: 2026-05-05 13:55

## Observed Behavior

`aiworker init --soul <preset>` prints (sanitized example shape):

```
[worker] id=w_xxxxxxxxxxxx
[worker] AIWORKER_BOOTSTRAP_TOKEN=wtk_<base64-ish>
[worker] save this token; it will not be printed again.
✔ [aiworker init] project-scope worker w_xxxxxxxxxxxx ready (...)
[aiworker init] next steps — Project Brain comes first; executor is bring-your-own
  1. Confirm scope: ...
  ...
```

Issues:

1. The bootstrap token is printed inline, on a normal-priority line, with
   a single trailing reminder. There is no visual containment (no banner,
   no colour change, no "STORE THIS NOW" framing) to discourage copy/paste
   of the whole `init` output into chat / GitHub issues / screenshots.
2. The 11-step "next steps" listing immediately follows the token, so the
   token scrolls off-screen quickly when the operator reads on. Many
   tooling pipelines (CI, tmux scrollback, IDE terminals) capture the full
   stdout; if the operator pastes it anywhere, the token leaks.
3. AGENTS.md security section explicitly warns:
   `AIWORKER_MASTER_KEY 必须离线备份；丢失会导致已注册 worker token 无法解密`
   — but the init flow does not surface the master key location, format, or
   "back this up" cue with the same prominence.

This skill's safety rules already require us never to write the printed
bootstrap token into reports. The fact that the rule is needed at all is a
hint that the surface is too easy to leak.

## Why this matters

- Bootstrap tokens are bearer credentials; leakage equals worker takeover.
- Operators who run `aiworker init` in CI, devcontainer wrappers, or
  remote-pairing sessions are at high risk because the entire stdout often
  ends up in artefact storage they don't control.
- Once leaked, the only mitigation is `aiworker token rotate`, but the
  operator has to *know* the leak happened. Today's UX makes silent
  exposure the default.

## Expected Behavior

1. Token printed inside a high-visibility block:

   ```
   ╔══════════════════════════════════════════════════╗
   ║ STORE THIS NOW — shown only once, do not paste   ║
   ║ AIWORKER_BOOTSTRAP_TOKEN=wtk_xxxxxxxxxxxxxxxxxxx ║
   ╚══════════════════════════════════════════════════╝
   ```

2. Optionally support `--token-file <path>` and print only the path on
   stdout, writing the token to a chmod 600 file the operator owns.
3. Print a masked confirmation by default (`AIWORKER_BOOTSTRAP_TOKEN=wtk_••••••••`)
   with the full value gated behind `--show-token` or written to the token
   file.
4. Master-key handling gets the same treatment: the init log says exactly
   where it lives and what to back up; if it is generated during init, the
   path is shown, not the value, and the value is reachable via a separate
   `aiworker token export-master-key --confirm` command with re-auth.

## Reproduction

```bash
mkdir token-leak && cd token-leak
$AIW init --soul developer
# Observe full token on stdout and the cramped reminder.
```

## Acceptance Criteria

1. `aiworker init` default output does not display the raw bootstrap token
   inline; the value is delivered via either a high-visibility framed block
   or an out-of-band token file.
2. CLI gains `--token-file` (or equivalent) and `--show-token` flags with
   docs and tests.
3. Master-key surface aligns with the same safer default; backup
   instructions live in the init output.
4. Existing scripts that grep `AIWORKER_BOOTSTRAP_TOKEN=` for first-run
   workflows have a documented migration path.

## Notes

- `aiworker token rotate` already exists for compromised tokens; the goal
  here is to make leakage less likely rather than to remove the recovery
  path.
