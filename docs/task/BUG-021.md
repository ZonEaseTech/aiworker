## Description

PLAN-023 intended `aiworker init` to default to project scope and create
`<project>/.aiworker/` in the current git repository. The real CLI entrypoint
does not do that. The side-effect bootstrap writes the resolved fallback home
back into `process.env.AIWORKER_HOME`, and `runInit()` later interprets that
derived value as an explicit operator override.

Observed behavior in an isolated git repo:

1. `aiworker init` reports `explicit-scope worker ... ready ($HOME/.aiworker)`.
2. No `<project>/.aiworker/` layout is created.
3. Existing project `aiworker scope` reports `explicit` and points persona paths
   at `.aiworker/local/workers/<workerId>/...`.
4. `aiworker scope` is documented as zero side effect, but the entrypoint mints
   `.env` before the command handler runs.

## In Progress Notes

Root fix: keep derived scope out of `AIWORKER_HOME`, make `init` own its dotenv
bootstrap flow, and add real CLI subprocess smokes with isolated `HOME`.

## Completion Notes

Implemented in `apps/cli/src/lib/bootstrap.ts`,
`apps/cli/src/commands/init.ts`, `apps/cli/src/commands/scope.ts`, and
`apps/cli/src/aiworker.ts`.

Key outcomes:

1. Side-effect bootstrap no longer writes derived scope into
   `AIWORKER_HOME`.
2. `init` now bootstraps the selected home explicitly for global, explicit,
   existing-project, and brand-new project modes.
3. `scope` is non-mutating and writes deterministic stdout.
4. Subprocess regression tests cover the real CLI entrypoint with isolated
   `HOME`.
