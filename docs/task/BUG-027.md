# BUG-027 Gateway chat accepted conversation id cannot be reused for continuation

- **status**: completed
- **priority**: P1
- **owner**: Codex
- **createdAt**: 2026-04-28 18:45
- **discoveredAt**: 2026-04-28 18:45
- **releaseTarget**: `@zonease/aiworker-cli@0.4.4`

## Description

During the `@zonease/aiworker-cli@0.4.3` test-server fleet smoke, a local
worker using `executor=codex/default` joined the test fleet successfully and
handled real Codex turns. Explicit gateway conversation ids work, but the
default `aiworker chat` continuation contract is broken.

Observed flow:

1. Operator ran `aiworker chat <workerId> "Reply exactly SESSION_ONE_043 and nothing else."`
   without `--conversation-id`.
2. Gateway returned `accepted.payload.conversationId` as
   `gw:<workerId>:<uuid>`.
3. Worker events for that turn used a worker-side conversation id
   `7af9c61a-c5f1-44f8-9f6d-0b5588c1fc19` and Codex replied with
   `SESSION_ONE_043`.
4. Operator reused the accepted id with
   `aiworker chat <workerId> "What exact marker..." --conversation-id gw:<workerId>:<uuid>`.
5. Gateway accepted the second turn as `gw:conv:gw:<workerId>:<uuid>`, which
   created a new worker-side session instead of continuing the first one. The
   worker could not recall the marker and replied with unrelated text.

Control check:

- When the operator supplied `--conversation-id explicit-043` on the first
  turn and reused the same id on the second turn, the worker kept the same
  worker-side session id and correctly returned `SESSION_EXPLICIT_043`.
- `/new ...` on that explicit id rotated the worker-side session id and the
  follow-up correctly returned `SESSION_RESET_043`.

Root cause candidate from code inspection:

- `GatewayDispatcher.handleChatSend()` synthesizes a random chat id
  `gw:<workerId>:<uuid>` when the operator omits `conversationId`.
- The response returns that synthetic chat id as `conversationId`.
- A later operator-provided `conversationId` is always wrapped as
  `gw:conv:<id>`, so reusing the returned id changes the session key.

## Acceptance Criteria

1. The `conversationId` returned by `chat.send` can be passed unchanged to the
   next `chat.send` call and continue the same logical worker session.
2. The gateway response and streamed event payloads expose a coherent
   user-facing session identifier, or the CLI clearly translates between
   gateway ids and worker session ids.
3. Add a focused gateway/dispatcher regression for omitted `conversationId`
   followed by reuse of the accepted id.
4. Re-run the test-server fleet to local Codex worker e2e: first turn without
   `--conversation-id`, second turn with the accepted id, and the second turn
   must recall the first marker.

## Notes

  `--conversation-id` reuse, Codex engine bindings, session status, and `/new`
  reset all passed in the 0.4.3 smoke.
- Keep the fix scoped to gateway conversation-id semantics before changing
  worker session store behavior.
- 2026-04-28 18:54 Codex investigation: root path is worker-side
  `GatewayDispatcher.handleChatSend()`. Returned gateway ids are not
  idempotent when reused because any provided `conversationId` is wrapped as
  `gw:conv:<id>`. Gateway event payloads also currently surface the
  worker-side `conversations.id`, not the accepted gateway chat id.
- 2026-04-28 19:02 Implemented the scoped fix: normalized already-accepted
  `gw:` ids without double wrapping, propagated `gatewayConversationId` on
  gateway-origin worker bus events, and mapped gateway event payloads back to
  the accepted user-facing id. Focused tests, changed-file ESLint, core
  typecheck, and the full `@zonease/aiworker-core` test suite passed. The
  live test-server fleet to local Codex worker e2e was not run from this
  workspace because the external gateway/worker smoke context was not
  available in the shell.
