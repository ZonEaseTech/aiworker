# BUG-079 Public Caddy ingress does not route fleet-hosted worker UI

- **status**: completed
- **priority**: P1
- **owner**: local
- **createdAt**: 2026-05-06
- **discoveredAt**: 2026-05-06 13:23
- **completedAt**: 2026-05-06 13:32
- **plan**: PLAN-136
- **relatesTo**: FEAT-040, PLAN-042, BUG-007, BUG-080

## Observed Behavior

The already-paired worker `w_8jbcm249cxn4` could not be opened through the
public fleet domain at `/w/w_8jbcm249cxn4/`.

Read-only production checks showed:

- `aiworker-gateway.service` was active and listening on `127.0.0.1:9218`.
- Direct gateway access to `/w/w_8jbcm249cxn4/` returned the Worker UI shell.
- Direct gateway access to `/w/w_8jbcm249cxn4/api/worker/info` returned worker
  info through the gateway bridge, with runtime/executor healthy.
- Caddy access to the same `/w/...` paths returned `404`.
- `/etc/caddy/Caddyfile` had handlers for `/admin*`, `/ws`, `/enroll-ws`, and
  `/health`, but no `/w*` handler, so the final fallback returned 404 before
  the request reached gateway.

## Expected Behavior

The public fleet domain should route `/w/<workerId>/` and
`/w/<workerId>/api/worker/*` to the gateway with the same external-auth
protection as `/admin*` and `/ws`.

## Actual Behavior

Caddy returned 404 for `/w/*`, preventing fleet-hosted Worker UI and gateway
bridge requests from reaching the gateway.

## Risk

P1 operational regression. The worker itself is paired and online, but the
single-domain fleet management path for non-same-host workers is unavailable
through the public ingress.

## Validation

After fix:

1. Caddy validates and reloads successfully.
2. Unauthenticated public `/w/w_8jbcm249cxn4/` access is fail-closed behind
   Caddy auth.
3. Loopback Caddy `/w/w_8jbcm249cxn4/` is no longer a fallback 404; it is
   matched by the protected route and returns `401 Unauthorized` without
   credentials.
4. Direct gateway `/w/...` remains healthy.
5. Direct gateway bridge errors, if any, are no longer Caddy 404s and should be
   diagnosed as worker presence / gateway protocol issues.

## Completion Evidence

- Remote `/etc/caddy/Caddyfile` backed up to
  `/etc/caddy/Caddyfile.bug079.20260506T132931Z.bak`.
- Remote `caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile`
  passed and `systemctl reload caddy` left Caddy active.
- Remote Caddy handlers now include `/admin*`, `/w*`, `/ws`, `/enroll-ws`, and
  `/health`.
- At the time of this fix, public unauthenticated
  `https://aiw.jbcnet.co.jp/w/w_8jbcm249cxn4/` and
  `/w/w_8jbcm249cxn4/api/worker/info` returned Caddy `401` instead of the
  previous `404`, proving the route reached the protected handler.
- Follow-up `BUG-081` moved `/w*` auth from Caddy Basic Auth to gateway worker
  bearer validation; the shell now returns `200`, and unauthenticated bridge
  API returns gateway `401 auth-required`.
- Direct gateway `/w/w_8jbcm249cxn4/` returns the Worker UI shell.
- Follow-up `BUG-080` captures the independent post-Caddy issue: the approved
  OTP worker reconnects to `/enroll-ws` as a plain node and is rejected with
  `wrong_path:expected_enroll_otp`, leaving the worker offline.
