# BUG-066 Brain decision layer (intent / capability / quality_gate) is heuristic-only and observe-only — does not match "Brain decision LLM" product positioning

- **status**: pending
- **priority**: P1
- **owner**:
- **createdAt**: 2026-05-05 14:10
- **discoveredAt**: 2026-05-05 13:57
- **relatesTo**: aiworker-release-debug skill goal "verify whether brain decision LLM really works"

## Observed Behavior

During 0.8.0 release validation across 5 Souls × 60 turns of `aiworker run`,
every event of type `orchestrator.intent_decision`,
`orchestrator.capability_decision`, and `orchestrator.quality_gate` was emitted
with:

```json
{
  "mode": "observe_only",
  "source": "intent-heuristic",
  "reason": "no-existing-conversation; heuristic intent=memory_update"
}
```

```json
{
  "mode": "observe_only",
  "source": "capability-registry",
  "reason": "S2 observe-only capability registry; selections are recorded but not enforced."
}
```

```json
{
  "mode": "observe_only",
  "source": "quality-gate",
  "evaluator": "heuristic",
  "gateMode": "observe",
  "reason": "heuristic quality gate passed"
}
```

No `source` value pointed at an LLM-backed decider. No event indicated that
the recorded selection was enforced; every event explicitly labelled itself as
`observe_only` and `not enforced`.

## Why this matters

- The product README, AGENTS.md, and the aiworker-release-debug skill all
  emphasise that AIWorker is a **Project Brain** with a brain decision layer
  that drives the LLM. The user explicitly asked us to "verify whether the
  brain decision LLM really works" during 0.8.0 release validation.
- The 0.8.0 reality observed across 60 turns is: brain decisions are made by
  pure heuristics (e.g. heuristic intent classification, capability selected
  by registry rule, quality gate scored by heuristic). LLMs are only used by
  the *executor* (claude-code / codex), not by the brain decision pipeline.
- Because every decision is also `mode: "observe_only"`, even the heuristic
  selections do not flow back into the executor prompt assembly — they are
  recorded to the event stream and DB but do not gate or shape the next step.
- This is a load-bearing positioning gap, not a stylistic one: any future
  feature that depends on LLM-driven brain decisions (smart capability
  selection, dynamic quality gates, intent-aware Soul routing) is currently
  blocked.

- CLI under test: published `@zonease/aiworker-cli@0.8.0` installed via

- Souls × engines:
  - `dev-claude-code` × `claude-code/default`
  - `dev-codex` × `codex/default`
  - `hr` × `claude-code/default`
  - `finance` × `codex/default`
  - `qa` × `claude-code/default`

Steps:

```bash
AIW=.npm-aiworker/node_modules/.bin/aiworker
mkdir release-0.8.0 && cd release-0.8.0
$AIW init --soul developer
$AIW executor select --engine claude-code --apply
$AIW run --chat-id smoke --message 'Hello, please describe your Soul.'
```

Inspect any `*-turnNN.log` produced by the multi-turn matrix (saved under
`release-0.8.0/logs/`). Every turn emits the heuristic `observe_only` events
described above; no turn shows an LLM-sourced brain decision.

## Expected Behavior

Either of:

1. The README / AGENTS.md / Soul positioning is updated to clearly say "the
   brain decision layer in 0.8.0 is heuristic + observe-only; an LLM-driven
   variant is on the roadmap", and the event payloads keep `source` explicit
   so any operator can tell at a glance whether a decision was LLM- or
   heuristic-derived.
2. A real LLM-backed decision implementation lands behind a flag, with
   `intent_decision.source = "intent-llm-..."` (or similar) and `mode` other
   than `observe_only` when the operator opts in. Heuristic stays as the
   safe default.

Either path is acceptable; what is unacceptable is shipping product copy that
implies an LLM brain layer while every decision is heuristic and inert.

## Acceptance Criteria

1. Decide and document the 0.8.x position (heuristic-only vs LLM-pluggable).
2. Make the "brain decision LLM is/isn't active" status visible at runtime —
   for example via `aiworker brain status` adding an `intentClassifier`,
   `capabilityRouter`, `qualityGate` block that reports `mode` and source.
3. If LLM mode is added, gate it behind an explicit opt-in (env or config),
   and add a focused test that asserts the produced `source` and `mode` change
   accordingly.
4. Update any external documentation (README, marketing copy) that promises a
   "Brain decision LLM" so it matches the shipped capability.
