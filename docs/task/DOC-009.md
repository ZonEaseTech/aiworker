## Background

The vertical Soul MVP docs still described the local product as a single
team/org Soul workspace. User architecture review clarified that this is the
wrong long-term foundation: one host should run one local daemon, and that
daemon should manage multiple Soul-bound workers. A worker is the Soul runtime
boundary; workspaces/projects, sessions, turns, artifacts, reviews, and durable
memory belong below that boundary.

Open Design remains useful as product grammar, but it has no worker layer
because it is a single-domain design-generation product. AIWorker must not map
OD's project directly to worker, and it must not keep Soul as only project
metadata.

## Goal

Record the target architecture contract and use it as the next refactor phase
goal:

- `1 host -> 1 local daemon -> N Soul workers`;
- `1 worker -> 1 Soul -> N workspaces/projects`;
- `1 workspace -> N sessions`;
- `1 session -> N turns / artifacts`;
- capabilities are owned by the Soul worker and inherited by workspaces;
- each turn, engine invocation, and artifact must record the capability or
  workflow version it used;
- engine handoff begins at the workspace session layer, aligned with external
  engine native sessions;
- `run` is not a product object; internal retry/debug/audit records are
  `engine_invocations`;
- local debug/startup should converge to one daemon lifecycle and one Web URL.

## Acceptance Criteria

- GOALS defines host, daemon, worker, workspace, session, turn, invocation, and
  capability ownership.
- Architecture docs map Open Design concepts to AIWorker concepts without
  collapsing OD project into AIWorker worker.
- Architecture docs define the target API/data/storage/debug contract for the
  multi-worker local daemon phase.
- Architecture docs define the file consumer contract: daemon-read source,
  engine-visible session cwd files, audit/replay files, and human/export files.
- Architecture docs state that this contract must be strictly followed unless
  implementation evidence proves it impossible or inferior, in which case a new
  proposal is required.
- README explains the model and no longer presents two-step API + Web startup
  as the intended operator path.
- PMA task, PMA plan, and changelog are synchronized.
