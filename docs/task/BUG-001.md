## Description

A bare-metal dev run (no docker) of `aiw serve` fails twice in a row out of
the box because two env vars default to paths that only make sense inside the
production container image:

1. `WORKER_DATA_ROOT` defaults to `/var/lib/aiworker`
   (`packages/core/src/config/worker.ts:35`). The orchestrator uses this root
   to materialise per-conversation workspaces; on a developer machine the
   `mkdir` fails with `EACCES`, and the next event is
   `Claude Code executor requires a workspace path`. Documented env vars in
   `docs/cli.md` and `apps/api/.env.example` do not even mention this var, so
   nobody knows to override it.
2. `WORKER_MIGRATIONS_FOLDER` defaults to `./drizzle/worker`
   (`packages/core/src/config/worker.ts:25`) — a path resolved against the
   current working directory. `apps/api/src/modes/worker.ts:48` consumes this
   value via `workerEnv.WORKER_MIGRATIONS_FOLDER` and feeds it directly into
   `runWorkerMigrations`. From the repo root the path resolves to
   `/home/ben/projects/aiworker/drizzle/worker`, which does not exist;
   `aiw serve` dies with `Can't find meta/_journal.json`.

   `apps/cli/src/context.ts:62` already does the right thing
   (`process.env.WORKER_MIGRATIONS_FOLDER ?? defaultWorkerMigrationsFolder`,
   the latter resolved from `import.meta.url` inside
   `@aiworker/storage-sqlite/worker`), so `aiw init` works; the divergence
   between the CLI and the worker server is the actual bug.

### Acceptance criteria

- A bare-metal dev run that exports only `AIWORKER_MASTER_KEY`,
  `INTERNAL_SHARED_SECRET`, `AIWORKER_HOME`, `WORKER_DB_PATH`, `PORT`,
  `AIWORKER_GATEWAY_PORT/HOST` works end-to-end:
  - `aiw init` mints identity (already works, must not regress).
  - `aiw serve` boots without `WORKER_MIGRATIONS_FOLDER` being set.
  - `aim chat` round-trips a message via gateway → worker → claude-code
    without `EACCES` on workspace creation and without the
    `Claude Code executor requires a workspace path` error.
- No reliance on any path under `/var/lib/aiworker` for either env var when
  the process runs outside the production container.
- Production container behaviour stays unchanged
  (`ops/compose/docker-compose.yml` and the Dockerfile still set absolute
  paths explicitly when needed).
