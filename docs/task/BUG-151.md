# BUG-151 Universal workbench engine readiness false positive

- **status**: completed
- **priority**: P0
- **owner**: codex

## Background

The mounted universal workbench currently passes
`engineReadiness={{ ready: true }}` directly from
`packages/soul-app-workbench/src/universal-workbench/client-entry.tsx`.
That creates a false positive: the composer remains enabled even when the
daemon has no configured BYOK key, the selected local CLI is missing, or the
selected engine id is not present in local settings.

The daemon session and turn paths already use local settings to select the
engine. The workbench package also already has `resolveEngineReadiness(...)`,
but the mounted browser client is not using that existing semantics.

## Acceptance Criteria

1. The mounted universal workbench reads the same Host local settings source
   used by session/turn execution.
2. Missing settings, missing engine ids, uninstalled local CLI engines and
   unconfigured BYOK mode render `ready: false` with a useful detail message.
3. Ready local CLI or BYOK settings render the real selected engine/provider
   information.
4. The create-session and continue-session composers stay disabled while
   readiness is false.
5. The fix stays within the Soul-owned mounted workbench and generic Host
   settings/engine bridge boundary; Host Web must not grow a universal
   workbench renderer or special branch.
6. Focused tests cover the mounted readiness source and disabled composer
   behavior.

## Scope

- `packages/soul-app-workbench/src/universal-workbench/client-entry.tsx`
- focused universal workbench package tests
- PMA and changelog tracking

## Non-Goals

- Do not redesign the settings dialog.
- Do not add Host-owned universal workbench rendering.
- Do not introduce app-domain engine configuration fields.
- Do not probe external engine auth or native session state beyond local
  settings readiness semantics.

## Resolution

The mounted universal workbench client now starts with loading readiness and
then reads `/api/local/settings`, the same Host local settings source used by
session and turn execution. It passes that settings object through the existing
`resolveEngineReadiness(...)` helper, so missing settings, unconfigured BYOK,
unknown engine ids and uninstalled local CLI engines keep the composer disabled
with a concrete readiness detail.

Ready settings now display the real selected engine/provider label instead of
the previous hard-coded `Engine bridge ready` false positive. Host Web remains a
generic micro-app mount container and does not render or branch on universal
workbench internals.
