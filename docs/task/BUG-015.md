## Description

`buildBearerAuth` 仅在 `buildManagementRoutes` 内部通过 `routes.use('*', ...)` 挂载（`apps/api/src/worker/management/routes.ts:80`），仅作用于 `/api/worker`（management）这一支；但 `apps/api/src/modes/worker.ts:171-173` 把 orchestrator / evolution / events 三个 sub-router 通过另起 `app.route(...)` 挂载，**不在 bearer 防护下**。

management/routes.ts:278-279 的注释甚至已经写道："bearer-auth 中间件已经对所有 `/api/worker/*` 生效"——意图与实现错位。

### 暴露面（worker HTTP 端口可达即生效）

- `POST /api/worker/orchestrator/tasks`（`apps/api/src/worker/orchestrator/routes.ts:20-26`）— 任意 prompt 投递，触发 LLM/executor 调用，attacker 直接通过 worker 跑 agent。
- `GET  /api/worker/orchestrator/tasks` / `/conversations[/:id/messages]`（同文件 15-37）— 拉取全部历史会话，含 user prompt + executor 输出。
- `GET  /api/worker/events/stream`（`apps/api/src/worker/events/routes.ts:14-30`）— SSE 实时流出全部内部事件（task lifecycle / channel inbound / executor token 流）。
- `POST /api/worker/evolution/drafts/:id/{approve,reject}`（`apps/api/src/worker/evolution/routes.ts:20-37`）— 任意人批准 / 拒绝 evolution 草稿（影响 brain / skill 的演化决策）。

### 用户可见影响

worker HTTP 端口可达者（loopback 默认信任、Caddy 后端、容器同网段、配置失误暴露公网……）即可执行上述操作。BUG-007 已经为 Caddy 反代做了 fail-closed basicauth，但 worker 自己的 4 个内部 API 完全无认证——一旦反代后侧的 trust 假设被打破（比如 dev 时 `aiworker serve --port 4000` 直接监听 0.0.0.0），attacker 直接 hit worker 即可。

## Acceptance criteria

1. **顶层守门**：`apps/api/src/modes/worker.ts` 顶层 `app.use('/api/worker/*', buildBearerAuth({ getIdentity: () => ({ tokenPlaintext: state.tokenPlaintext }) }))`，覆盖 orchestrator / evolution / events / management 全部 sub-router。`/health` 与 channels webhook 仍保持 public（监控 + 平台回调）。
2. **避免双中间件**：移除 `buildManagementRoutes` 内部的 `routes.use('*', buildBearerAuth(...))`；后续 management 测试改用外层 wrapper app 来覆盖 auth 行为。
3. **e2e 回归测试**：在 `apps/api/src/modes/worker.bearer-auth.test.ts`（新文件）通过 `bootstrapWorkerApp` 起一份真实 app，覆盖：
   - 未带 token 调 `POST /api/worker/orchestrator/tasks` → 401
   - 带正确 token → 201（或合理的业务 status）
   - 未带 token 调 `GET /api/worker/events/stream` / `/api/worker/evolution/drafts` / `/api/worker/info` → 401
   - `/health` + channels webhook 仍可在无 token 下访问（不被误伤）
4. **现有 management 测试不退化**：`apps/api/src/worker/management/routes.test.ts` 通过 wrapper app 重新覆盖 401 / 200 case；`bearer-auth.test.ts` 不变。
5. lint / typecheck / `bun test` 全绿。

- 新增 `apps/api/src/modes/worker.bearer-auth.test.ts`：真实 `bootstrapWorkerApp`（用临时 worker.db + master key），fetch 上述 4 个端点。

### 不变量

- `/health` 不在 `/api/worker/*` 范围内，bearer-auth 不会拦它（监控 / 探活继续可用）。
- channels webhook 挂在 `/`，不在 `/api/worker/*` 范围，仍由 channel 自己的 signature 校验把关（Telegram / WhatsApp / Lark）—— BUG-015 不动这条。
- bearer-auth 中间件按 `getIdentity` 闭包延迟读 `state.tokenPlaintext`，token rotate 不需要重挂中间件（已有现成测试 covered）。
- hot-reload 友好：bearer-auth 不依赖 runtime，只依赖 `state.tokenPlaintext`，runtime swap 不影响。
