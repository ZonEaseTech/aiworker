# BUG-007 Public Caddy ingress bypasses gateway authN (loopback misidentification)

- **status**: completed
- **priority**: P0

## Description

Gateway authN (`apps/gateway/src/auth/loopback.ts` + `auth/token.ts`)
unconditionally allows the connection when
`Bun.serve.requestIP(req).address` reports a loopback address. The
public-HTTPS deploy topology (`docs/deployment-public-https.md`)
runs Caddy on the host with `reverse_proxy 127.0.0.1:3000`. After the
reverse proxy, the source IP gateway sees is **always `127.0.0.1`**.
The combination means **any request that reaches Caddy port 80
authenticates as a trusted loopback operator**, with no token check.

In the current public deployment topology
(`gateway.example.test` → Cloudflare orange-cloud → host :80 → Caddy
→ gateway :3000), this means anyone who can resolve the public
hostname is already an operator. Cloudflare is not an authN layer.

This is documented in `docs/deployment-public-https.md:175` as a
positive feature ("浏览器经 Caddy 反代属于 gateway 视角的 loopback...
不需要再叠一层 basic auth") — that documentation is **wrong** and
must be corrected as part of this fix.

The fix is purely operational (Caddy config); no Go/TS code change.
Bare-metal and systemd deployments are not affected (they expose
`:3000` only on loopback by default; no Caddy hop). Local docker
compose without public exposure is also not affected
(`127.0.0.1:3000:3000` binding).

### Threat model

- **Public production** (Cloudflare + Caddy + gateway): GO if and only
  if Caddy enforces its own authN (basic-auth, IP allowlist, mTLS, or
  Zero Trust).
- **Internal network** (no Caddy, gateway listens on internal IP only,
  remote operators carry `INTERNAL_SHARED_SECRET`): unaffected.
- **Bare-metal localhost dev**: unaffected.

### Acceptance criteria

- `ops/caddy/Caddyfile.tmpl` no longer reverse-proxies an
  unauthenticated `:80` site. It either fails to load or rejects
  unauthenticated requests with `401`.
- Implementation choice: **fail-closed**. Caddy must not start with a
  default-allow-all config; missing credentials should produce a load
  failure, not silent fallback.
- `docs/deployment-public-https.md`:
  - The wrong "Caddy 反代属于 gateway 视角的 loopback ... 不需要 basic auth"
    sentence is replaced with a correct statement of the threat model.
  - A "Caddy basic-auth setup" subsection is added with concrete steps
    (generate bcrypt hash, install snippet to host, validate, reload).
  - The "故障排查" line that suggests "通过 Caddy 反代进入" as a workaround
    for the loopback check is annotated as the now-fixed bug.
- `docs/deployment.md` (the bare-metal/systemd doc) gets a one-liner
  pointer: if you choose to add a Caddy/nginx in front of bare gateway,
  read the BUG-007 setup before doing so.
- Changelog entry under `[BUG-P0]` describing root cause, threat
  surface, fix, and migration steps for already-deployed hosts.

## Notes

### Implementation choice

`Caddyfile.tmpl` uses `import auth.snippet`; the snippet file lives at
`/etc/caddy/auth.snippet` on the host, is created by the operator, is
**not** committed to git, and contains a single `basicauth { ... }`
directive with bcrypt-hashed credentials. If the snippet is missing,
Caddy refuses to load — **fail-closed**.

This avoids:
- Committing credentials to git (per CLAUDE.md security policy).
- Adding placeholder substitution to `scripts/deploy.ts` (more code,
  more failure modes).
- Adding a separate Caddy site for "internal vs public" — same gateway
  serves both; trust boundary is the IP path, not the domain.

### Migration for already-deployed host (gateway.example.test)

```sh
# 1. Generate hash on workstation:
caddy hash-password --plaintext '<your-secret>'   # → $2a$14$...

# 2. ssh onto the host and create the snippet:
sudo tee /etc/caddy/auth.snippet >/dev/null <<EOF
basicauth {
  operator $2a$14$...real-hash-here...
}
EOF
sudo chown caddy:caddy /etc/caddy/auth.snippet
sudo chmod 0640 /etc/caddy/auth.snippet

# 3. Run deploy reload-caddy (uses the new Caddyfile.tmpl):
bun run scripts/deploy.ts reload-caddy

# 4. Distribute credentials to operators (operator must store
#    in their aim/web client; aim CLI accepts --gateway-token).
```

### Open questions for follow-up

- The web SPA currently sends bearer over WS connect frame, not HTTP
  Authorization. basicauth gates on the HTTP upgrade request — the
  browser's `WebSocket()` API does not support sending HTTP basic auth
  natively across all browsers. Workaround: `wss://operator:<pass>@host/ws`
  URL form (deprecated in modern browsers). May force a cookie-based
  auth or token-in-URL path for the web client. Tracked separately
  if needed.
- Pure host-machine `aim` CLI (without Caddy in path) is unaffected.
