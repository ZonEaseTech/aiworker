## Description

The test-server fleet to local Codex worker path can deliver chat requests and
stream completion events, but a second turn in the same gateway conversation
does not receive the first turn's worker history.

Observed on 2026-04-28 with `@zonease/aiworker-cli@0.4.1` on the test server
and a local worker running `executor=codex/default`:

1. Fleet sent `chat.send` with `conversationId=mem-20260428-codex`.
2. First turn asked the worker to remember `MEMKEY-774-CERULEAN`; the worker
   replied `STORED`.
3. Second turn used the same `conversationId` and asked for the exact key.
4. The worker replied with the internal conversation UUID instead of
   `MEMKEY-774-CERULEAN`.
5. `worker.db` shows all four messages persisted in the same conversation, so
   the storage and gateway conversation routing paths are not the failing layer.

Root cause from code inspection: `Orchestrator.run()` loads the recent worker
message window and passes it to `executor.run()`, but `CodexExecutor` extracts
only the latest user message and starts a fresh Codex thread for every run.
That makes worker.db history non-authoritative for Codex turns.

## Acceptance Criteria

1. Codex executor receives the worker history window for every turn, not only
   the latest user message.
2. The implementation keeps compatibility with both legacy
   `thread_start` / `newTurn` and current `thread/start` / `turn/start`
   app-server protocols.
3. Worker.db remains the authoritative conversation history source; engine-side
   caches may accelerate but must not be required for correctness.
4. Add focused Codex executor tests that assert prior user and assistant
   messages are included in the app-server request.
5. Rerun a test-server fleet to local Codex worker e2e memory check where turn
   two correctly returns a key stored in turn one using the same
   `conversationId`.

## Notes

- This is related to the broader FEAT-031 / PLAN-021 long-memory work, but it is
  narrower: same gateway conversation, same worker, same engine.
- PLAN-021 already calls out the general "worker history vs engine history"
  double-track problem for CLI engines; this bug is the concrete Codex
  regression proven by e2e.
- OpenClaw reference points for this slice: session key reuse maps to a current
  session id; `/new` and `/reset` rotate that id; CLI/Codex backends keep a
  provider-side session binding when available, but the gateway-visible
  transcript remains the user-facing source of truth.

## Completion Notes

Implemented the minimal OpenClaw-style session slice:

1. Codex executor now renders the full worker history window from
   `AgentRunInput.messages` into both legacy `newTurn` and current
   `turn/start` requests.
2. Gateway `chat.send` recognizes `/new` and `/reset`, strips an optional
   command body, and marks the envelope as a session reset.
3. Orchestrator reset handling closes the current open worker conversation for
   the same chat key and creates a fresh one before running the reset body.
4. Focused tests cover Codex history injection and gateway reset conversation
   rotation.
