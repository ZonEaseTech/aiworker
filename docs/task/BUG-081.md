# BUG-081 Fleet-hosted Worker Admin is blocked by Caddy Basic Auth before worker bearer auth

- **status**: completed
- **priority**: P1
- **owner**: local
- **createdAt**: 2026-05-06
- **discoveredAt**: 2026-05-06 13:49
- **completedAt**: 2026-05-06 13:58
- **plan**: PLAN-138
- **relatesTo**: BUG-079, BUG-080, FEAT-040, PLAN-042

## Observed Behavior

After `BUG-079`, `/w/w_8jbcm249cxn4/` was routed through Caddy but protected
by Caddy Basic Auth. The user had already entered the worker bearer token in
the Worker Admin, but API calls under `/w/.../api/worker/*` were still stopped
by Caddy.

Caddy logs showed the shell/static request could pass Basic Auth as
`user_id='operator'`, while subsequent Worker Admin API fetches carried
`Authorization: Bearer ...` and were rejected by Caddy Basic Auth with
`401`. A browser request can only send one `Authorization` header, so the
worker bearer header overwrote the Basic Auth header.

## Expected Behavior

Fleet-hosted Worker Admin should use the worker bearer token as the `/w/*`
authorization boundary. Caddy should not require Fleet/operator Basic Auth for
`/w*`.

## Actual Behavior

Caddy protected `/w*` before gateway could see the worker bearer token, so the
correct Worker Admin token could not authenticate bridge requests.

## Fix

- Removed Caddy Basic Auth from `/w*`.
- Added gateway-side bearer validation before any `/w/:workerId/api/worker/*`
  bridge request is forwarded to the worker.
- Gateway decrypts the registered worker token from `registered_workers` and
  compares it with the presented bearer token using constant-time comparison.
- Static Worker Admin shell under `/w/:workerId/` remains accessible so the UI
  can prompt for a worker token; API bridge requests without a valid token
  return `401` with `WWW-Authenticate: Bearer`.
