# BUG-045 Orchestrator task rows stay queued after successful worker execution

- **status**: completed
- **priority**: P1
- **owner**: Codex
- **createdAt**: 2026-05-02 20:39
- **discoveredAt**: 2026-05-02 20:26
- **completedAt**: 2026-05-02 21:46
- **plan**: PLAN-068

## Observed Behavior

Worker Admin and HTTP task submissions inserted rows into `agent_tasks`, but
successful Codex-backed execution did not update those rows beyond the initial
`queued` state. The assistant messages were persisted in `messages`, yet the
corresponding `agent_tasks.status`, `conversation_id`, `finished_at`, `result`,
and `error` fields remained unset.

The related `conversations.task_id` field also remained null for conversations
whose `chat_id` was `task:<task-id>`.

Relevant code pointers:

- `packages/core/src/worker/orchestrator/service.ts` `submitTask()` inserts an
  `agentTasks` row as `queued` and starts async ingestion.
- `packages/core/src/worker/orchestrator/service.ts` `createConversation()`
  emits a `taskId` in the event payload but does not persist it on the
  conversation row.
- `packages/storage-sqlite/src/worker/schema.ts` already has task lifecycle
  fields for running/succeeded/failed/cancelled, conversation link, finish time,
  result, and error.

## Expected Behavior

Task rows should reflect the real lifecycle of submitted work and be joinable
to the conversation that processed the task.

## Reproduction

1. Submit a Worker Admin Chat message or call `POST
   /api/worker/orchestrator/tasks`.
2. Wait for the assistant reply to be persisted successfully.
3. Query `agent_tasks` and `conversations` in the worker database.
4. Observe the task still marked `queued` with no conversation/result/finish
   metadata.

## Acceptance Criteria

1. Task status transitions are persisted from `queued` to `running`, then to
   `succeeded` or `failed`/`cancelled`.
2. `agent_tasks.conversation_id` and `conversations.task_id` are populated for
   task-backed conversations.
3. Successful tasks persist enough result metadata for the Worker Admin task
   view to explain what happened.
4. Failed tasks persist a redacted error and completion timestamp.
5. Storage/orchestrator tests cover success and failure lifecycle updates.
